# Strata AutoSearch Product Direction

Status: Draft product direction

AutoSearch is a future Strata capability for optimizing retrieval recipes
against a user's own dataset, questions, and golden answers.

It is not implemented today. This document records the product direction so the
recipe, retrieval, branching, control-plane, and intelligence architecture can
leave the right openings without prematurely baking AutoSearch into the V1
engine contract.

## Thesis

Search quality is usually dataset-specific.

General defaults can be good, but the best settings for legal discovery,
customer support, biomedical notes, source code, product catalogs, meeting
transcripts, and event logs are different. Users normally discover those
settings through weeks or months of manual tuning:

1. Try a BM25 setting.
2. Change chunk size.
3. Change embedding model.
4. Change hybrid weights.
5. Change reranker window.
6. Re-run the same test queries.
7. Compare results by hand.
8. Repeat.

Strata should turn that into a product workflow.

```text
dataset + golden answers + base recipe
  -> AutoSearch experiment loop
  -> optimized recipe + evaluation report + provenance
```

The goal is not to expose more knobs to users. The goal is to let users provide
examples of good retrieval and have Strata discover the best recipe for their
data.

## Product Promise

AutoSearch should let a user say:

```text
Here is my dataset.
Here are 50-100 example queries with the records I expect.
Find the best search recipe for this task.
```

Strata then runs controlled retrieval experiments and returns:

1. The best recipe.
2. The quality improvement.
3. The cost and latency tradeoff.
4. Which knobs changed.
5. Which examples improved or regressed.
6. Whether the result requires reindexing, re-embedding, or a rebuild.
7. Enough provenance to reproduce the result.

The product should feel like:

```text
months of retrieval tuning compressed into a few hours
```

## Non-Goals

AutoSearch does not mean:

1. Mutating engine internals.
2. Replacing recipes.
3. Introducing a hidden search engine.
4. Letting an LLM bypass source correctness, branch isolation, or temporal
   rules.
5. Guaranteeing globally optimal search quality.
6. Running expensive cloud model calls without explicit user policy.
7. Creating visible branch clutter by default.
8. Making AutoSearch required for basic search.

AutoSearch optimizes recipes. It does not rewrite Strata's retrieval engine.

## Core Model

AutoSearch operates over five concepts:

1. Evaluation set.
2. Base recipe.
3. Knob registry.
4. Experiment plan.
5. Result recipe.

### Evaluation Set

An evaluation set is a collection of examples.

Each example should include:

1. Query text or retrieval request.
2. Expected result `EntityRef`s.
3. Optional graded relevance per result.
4. Optional expected citations.
5. Optional negative examples.
6. Optional required filters, branch, space, or time context.
7. Evaluation metric preference.

Example shape:

```text
EvalExample {
    query: "refund after cancellation",
    expected: [
        { ref: json:ticket:421, relevance: 3 },
        { ref: json:ticket:817, relevance: 2 },
        { ref: event:account:closed:991, relevance: 1 },
    ],
    branch: "main",
    space: "support",
    metric: "ndcg@10",
}
```

This is conceptual shape, not a required Rust type.

### Base Recipe

The base recipe is the starting point.

It may be:

1. A built-in recipe.
2. A dataset recipe.
3. A branch-local recipe.
4. A user-supplied inline recipe.
5. A previously optimized AutoSearch recipe.

AutoSearch produces recipe variants. It should not mutate the base recipe
in-place unless the user explicitly asks to overwrite it.

### Knob Registry

The knob registry describes which recipe fields AutoSearch is allowed to vary.

Every knob needs metadata:

1. Name.
2. Recipe path.
3. Type.
4. Default.
5. Allowed range or allowed values.
6. Cost class.
7. Expected effect.
8. Whether it requires reindexing.
9. Whether it requires re-embedding.
10. Whether it requires vector index rebuild.
11. Whether it requires model runtime.
12. Compatibility with source types and runtime profiles.
13. Safety constraints.

Example:

```text
Knob {
    name: "bm25.k1",
    recipe_path: "retrieve.bm25.k1",
    type: float,
    range: 0.2..2.0,
    default: 0.9,
    requires_reindex: false,
    cost: cheap,
}
```

The registry is critical. Without it, AutoSearch becomes ad hoc trial code.

### Experiment Plan

An experiment plan is the list of recipe variants to test and the order in
which to test them.

Plans may be generated by:

1. Simple grid search.
2. Random search.
3. Coordinate descent.
4. Successive halving.
5. Bayesian optimization later.
6. Local LLM-guided planning.

The important direction is local LLM-guided planning. A local model can inspect:

1. Dataset profile.
2. Base recipe.
3. Previous experiment results.
4. Knob metadata.
5. Quality failures.
6. Cost constraints.

Then it proposes the next recipe variants to evaluate.

The LLM is a planner, not an authority. It proposes experiments. Strata
validates every recipe, enforces knob bounds, executes retrieval, scores
results, and records provenance.

### Result Recipe

The result is a normal recipe.

It may be saved as:

1. A branch-local recipe.
2. A dataset recipe.
3. A named user recipe.
4. A report-only recommendation.

The output should explain:

1. What changed from the base recipe.
2. Why the change won.
3. Which metrics improved.
4. Which metrics regressed.
5. What derived state must be rebuilt.
6. What model/runtime dependencies it introduces.

## Knob Categories

AutoSearch should eventually cover the major industry-standard search knobs.
V1-level retrieval may support only a subset, but the product direction should
leave room for parity.

### Text Retrieval Knobs

Examples:

1. BM25 `k1`.
2. BM25 `b`.
3. Stopword policy.
4. Stemmer.
5. Phrase boost.
6. Phrase slop.
7. Phrase filter versus phrase boost.
8. Proximity scoring enabled/disabled.
9. Proximity window.
10. Proximity weight.
11. Field weights.
12. Candidate count.
13. Snippet strategy.

### Vector Retrieval Knobs

Examples:

1. Embedding model.
2. Embedding dimension.
3. Distance metric.
4. Vector normalization.
5. Candidate count.
6. Exact versus ANN search.
7. ANN build parameters.
8. ANN search parameters.
9. User vector collection selection.
10. Shadow vector collection selection.

### Chunking And Projection Knobs

Examples:

1. Chunk size.
2. Chunk overlap.
3. Chunk boundary strategy.
4. Which fields are projected.
5. Metadata included in projection text.
6. Title/body weighting.
7. Event payload versus event metadata inclusion.
8. JSON path inclusion/exclusion.

These knobs often require reindexing or re-embedding, so they are more
expensive than scoring-only knobs.

### Hybrid Fusion Knobs

Examples:

1. Fusion method.
2. RRF `k`.
3. Text/vector weights.
4. Graph weight.
5. Score normalization.
6. Candidate pool sizes.
7. Deduplication key.
8. Tie-breaker policy.

### Graph Retrieval Knobs

Examples:

1. Max hops.
2. Relationship types.
3. Direction.
4. Graph boost.
5. Path weighting.
6. Ontology boost.
7. Dangling-reference policy.
8. Whether graph expands candidates, reranks candidates, or explains results
   only.

### Expansion And Rerank Knobs

Examples:

1. Expansion strategy.
2. Expansion model.
3. Number of expansion variants.
4. HyDE enabled/disabled.
5. Expansion cache policy.
6. Reranker model.
7. Rerank top-N.
8. Rerank blend weights.
9. Minimum candidate threshold.

### RAG Knobs

Examples:

1. Context hit count.
2. Context token budget.
3. Context packing strategy.
4. Citation strategy.
5. Prompt template.
6. Generation model.
7. Answer style.

RAG quality evaluation is harder than retrieval quality evaluation. AutoSearch
should optimize retrieval quality first and treat RAG tuning as a later layer.

### Execution Knobs

Examples:

1. Max latency.
2. Max candidates.
3. Parallelism.
4. Model-call budget.
5. Rebuild budget.
6. Runtime profile.
7. Cache policy.
8. Freshness policy.

Execution knobs prevent AutoSearch from finding a high-quality recipe that is
too slow or too expensive to use.

## Metrics

AutoSearch needs objective metrics.

Retrieval metrics:

1. Recall at K.
2. Precision at K.
3. MRR at K.
4. nDCG at K.
5. Hit rate.
6. Mean rank of first relevant result.

Operational metrics:

1. Median latency.
2. P95 latency.
3. Candidate count.
4. Index size.
5. Rebuild time.
6. Embedding cost.
7. Model-call count.
8. Memory usage.

RAG metrics later:

1. Citation coverage.
2. Groundedness.
3. Answer completeness.
4. Refusal correctness.
5. Token cost.

The default should optimize quality first within user-declared cost and latency
constraints.

## LLM-Guided Planning

The local LLM planner is the distinctive version of AutoSearch.

The model may propose:

1. Which knob to tune next.
2. Which values to try.
3. Whether a poor result suggests a text, vector, graph, chunking, or fusion
   issue.
4. Whether enough signal exists to stop.
5. Whether the evaluation set is too small or contradictory.
6. Whether a result improved one subset while hurting another.

The model must not:

1. Write directly to source data.
2. Bypass recipe validation.
3. Bypass knob bounds.
4. Modify hidden engine state.
5. Claim success without metric evidence.
6. Upload datasets or golden answers without explicit policy.
7. Use network models when the user selected local-only mode.

Strata should treat the LLM's output as a proposal:

```text
LLM proposal
  -> recipe variant validation
  -> bounded execution
  -> metric scoring
  -> provenance recording
  -> accept/reject based on evidence
```

This keeps the system agentic without making correctness depend on trusting the
model.

## Branching Model

Branches are a natural fit for AutoSearch, but the product must avoid visible
branch clutter.

AutoSearch may use:

1. Hidden experiment branches.
2. Temporary experiment contexts.
3. Branch-local recipe variants.
4. Branch-local derived-state rebuilds.
5. Branch-local reports.

User-visible branches should not be created by default. The user should see an
AutoSearch run, not 25 random branches.

A good visible model:

```text
AutoSearch run: support-hybrid-2026-05-11
Base branch: main
Base recipe: hybrid
Best recipe: support-hybrid-v3
Quality: nDCG@10 +18.4%
Latency: +7ms median
Saved as: branch recipe "support-hybrid-v3"
```

Experiment branches or contexts may be retained only if the user asks for
debugging or reproducibility.

## Provenance

AutoSearch provenance is mandatory.

Each run should record:

1. Dataset identity.
2. Branch and version/timestamp frontier.
3. Evaluation set identity and hash.
4. Base recipe identity and hash.
5. Knob registry version.
6. Planner identity: manual, grid, random, LLM model, or other.
7. Every recipe variant tested.
8. Every metric result.
9. Derived-state rebuilds performed.
10. Model calls made.
11. Runtime profile.
12. Random seeds.
13. Stopping reason.
14. Winning recipe identity and hash.

This enables reproducibility and prevents "the AI said this is better" from
becoming the product contract.

## User Experience

The ideal workflow:

```text
strata autosearch create support-eval --from examples.json
strata autosearch run support-eval --recipe hybrid --budget 4h --local-only
strata autosearch report latest
strata recipe save support-hybrid-v3 --from autosearch/latest
```

The exact CLI is illustrative.

SDK shape:

```text
db.autosearch()
  .evaluation_set("support-eval")
  .base_recipe("hybrid")
  .budget(hours=4)
  .planner("local-llm")
  .constraints(latency_p95_ms=250)
  .run()
```

Users should not need to understand all knobs to benefit from AutoSearch. They
should only need:

1. A dataset.
2. A representative set of questions.
3. Golden answers or graded relevance.
4. Quality/cost constraints.
5. A place to save the winning recipe.

## Architecture Constraints

AutoSearch should preserve these boundaries:

1. Recipes are the optimization unit.
2. The retrieval engine remains deterministic for a fixed recipe, branch,
   temporal context, and source state.
3. Source data is never modified by recipe experiments.
4. Derived state may be rebuilt in isolated experiment contexts.
5. Engine validates recipes and executes deterministic retrieval.
6. Intelligence/inference proposes variants and runs model-dependent stages.
7. Storage sees ordinary rows, branches, versions, and derived-state writes.
8. Experiment metadata lives in control-plane rows or explicit run artifacts.
9. Golden answers are user data or control-plane data with clear privacy rules.
10. StrataHub/private hubs may later store, share, or compare recipes and
    evaluation sets, but local AutoSearch must work without a hub.

## Privacy And Safety

AutoSearch can touch sensitive data because evaluation sets often include
queries, expected records, and examples of what users care about.

Rules:

1. Local-only mode must be available.
2. Golden answers must not be uploaded without explicit user action.
3. Query text and result references are sensitive metadata.
4. Experiment reports should redact values where configured.
5. Remote model use must be explicit.
6. Fleet or hub reporting must not include evaluation contents by default.

## Initial Product Scope

A sensible first implementation would support:

1. Evaluation sets with query plus expected `EntityRef`s.
2. Built-in metrics: recall@K, MRR@K, nDCG@K.
3. Base recipe plus generated recipe variants.
4. Text, vector, and hybrid knobs only.
5. Local deterministic planners: grid, random, coordinate descent.
6. Optional local LLM planner.
7. No RAG answer optimization.
8. Hidden experiment contexts.
9. Full provenance and report output.
10. Save winning recipe as branch-local or named recipe.

Graph, RAG, cross-branch evaluation, StrataHub-shared benchmarks, and
organization recipe catalogs can follow.

## Open Questions

1. Where should evaluation sets live: user data, control-plane rows, or external
   files?
2. Should golden answers refer only to `EntityRef`s, or can they include answer
   text and citation spans?
3. How should AutoSearch handle conflicting golden answers?
4. How many built-in metrics should ship before this becomes product-facing?
5. Should LLM planners be allowed to propose new chunking/projection schemas, or
   only scoring-stage knobs at first?
6. How should experiment-derived indexes be cleaned up after interrupted runs?
7. Should AutoSearch run against a fixed branch version by default?
8. What is the minimum report needed for users to trust the winning recipe?
9. How should StrataHub/private hubs share recipes without sharing private
   evaluation sets?
10. What is the safe default budget on small devices?

## Bottom Line

AutoSearch is the reason recipes exist.

Recipes make retrieval behavior explicit. AutoSearch turns that explicit
configuration into an optimization surface. The local LLM planner can make the
search process intelligent, but Strata must keep the hard boundary:

```text
LLM proposes. Strata validates, executes, measures, and records.
```

That gives Strata a path to search quality that ordinary embedded databases and
plain vector stores do not have.
