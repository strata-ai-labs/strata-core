## Objective

Add lifecycle assurance depth without changing lifecycle semantics.

L8O turns the direct unit suites from L8A-L8N into broader generated, fault,
crash/reopen, and fuzz-entry coverage. The slice should prove operation
ordering and recovery safety across sequences, not only isolated examples.

L8O implements:

1. a lifecycle script decoder that drives production lifecycle/testkit surfaces;
2. model-backed counters for every lifecycle phase family;
3. direct fault-window tests for durable publication and close phases;
4. localfs crash/reopen scenarios for durable boundaries that require real
   persistence;
5. fuzz target entry points and checked-in seed corpora that call distinct
   lifecycle contracts;
6. generated assurance over recovery, maintenance, retention, quarantine,
   table rewrite, close, and health facts;
7. source/fuzz/crash guardrails needed by L8P closeout.

L8O must not add product lifecycle API, public maintenance commands, engine
callbacks, StrataHub behavior, or new storage semantics. If a generated or fault
test reveals missing implementation behavior, fix that behavior in the owning
module and record it in the porting log.

## Old-Code Porting Map

The old codebase is evidence for failure windows and sequencing. L8O does not
port old APIs.

| Old source | Behavior to preserve in assurance | Storage-next assurance shape |
|---|---|---|
| `crates/engine/src/database/lifecycle.rs` | Close gates new work, drains/cancels background work, syncs durable state, and releases ownership in order. | Generated close scripts and fault tests cover close admission, quiesce timeout, WAL sync failure, manifest failure, guard release, retry, and double close. |
| `crates/engine/src/background.rs` | Background task order and cancel/drain policy must be deterministic under shutdown. | Maintenance script model drives enqueue, coalesce, run, cancel, drain, fault, close, and retry without sleeps or threads. |
| `crates/storage/src/durability/recovery.rs` | Recovery classifies corrupt/missing manifests, snapshots, WAL tails, and tables without panics. | Recovery fuzz and generated contracts feed corrupt fixture descriptions and assert typed health/failure. |
| `crates/storage/src/durability/recovery_bootstrap.rs` | Bootstrap must catch up durable commit state and fail closed on replay mismatch. | Bootstrap script routes cover checkpoint-only, WAL-tail, unresolved durable gates, timeline mismatch, and failed replay. |
| `crates/storage/src/durability/checkpoint_runtime.rs` | Checkpoint and manifest publication have explicit partial-progress windows. | Fault/crash tests cover snapshot-published/manifest-not-updated and manifest-updated/WAL-not-truncated windows. |
| `crates/storage/src/durability/compaction/wal_only.rs` | WAL truncation is proof-driven and recoverable. | Generated checkpoint/retention scripts assert truncation never exceeds model-proven watermarks. |
| `crates/storage/src/segmented/recovery.rs` | Table-object recovery and degraded state classify missing/corrupt objects. | Recovery and retention scripts cover missing table objects, lossy degradation, and retained health debt. |
| `crates/storage/src/segmented/quarantine_protocol.rs` | Quarantine happens before purge and repair reports facts without inventing state. | Quarantine crash/fault scripts cover inventory-published/source-not-moved, quarantined-not-purged, stale proof, and repair inconclusive routes. |

Do not port:

1. engine public database lifecycle APIs;
2. primitive freeze/rebuild callbacks;
3. IPC/server shutdown behavior;
4. product background worker threads;
5. product logs or user-facing recovery wording;
6. raw filesystem access inside lifecycle production code;
7. old path-based storage constructors.

## Scope

L8O implements:

1. `LifecycleScript` or equivalent deterministic script decoder in the testkit;
2. a lightweight independent lifecycle model for visible state, durable object
   families, deletion safety, health class, and close state;
3. generated property checks over the composed script contract;
4. fault fixtures for capability/open, recovery, bootstrap, flush, checkpoint,
   retention, quarantine, purge, repair, table rewrite, and close phases;
5. localfs crash/reopen cases for durable windows that cannot be proven with
   pure in-memory fakes;
6. fuzz targets:
   - `lifecycle_recovery`;
   - `lifecycle_maintenance`;
   - `lifecycle_retention`;
7. checked-in seed corpora for each lifecycle fuzz target;
8. testkit counters that distinguish canonical smoke coverage from input-driven
   generated coverage;
9. integration tests that execute the generated contract under default feature
   sets;
10. source guards that keep assurance code in tests/testkit/fuzz and prevent
    lifecycle production drift;
11. porting-log entries for shipped files, preserved behavior, intentional
    changes, deferred crash/fuzz depth, and verification.

L8O does not implement:

1. L8 closeout inventory or final command matrix enforcement; that is L8P;
2. public lifecycle API exposure; that is L9;
3. new retention, checkpoint, flush, quarantine, close, or recovery semantics;
4. new background worker implementation;
5. product crash runner or external process supervisor;
6. exhaustive model checking or loom/shuttle concurrency;
7. object-store distributed lease fault simulation;
8. StrataHub sync behavior.

## Assurance Model

The L8O model should be deliberately small and storage-shaped.

Model state:

1. lifecycle state: new, opening, recovering, open, closing, closed, failed;
2. storage mode: cache, durable standard, durable always, object candidate;
3. visible commit version;
4. durable checkpoint watermark;
5. flush watermark;
6. WAL record set by version;
7. snapshot set by snapshot id and covered version;
8. table-object set grouped by reachable, orphaned, quarantined, purged;
9. maintenance queue summary;
10. recovery health class and fault families;
11. close phase summary and retryability.

Model operations:

1. open cache;
2. open durable empty;
3. recover durable with checkpoint/WAL/tables;
4. cache commit;
5. durable commit;
6. rotate/freeze;
7. flush;
8. checkpoint;
9. truncate WAL;
10. compact/materialize;
11. retention proof;
12. quarantine;
13. purge;
14. repair;
15. close;
16. inject fault;
17. crash/reopen.

Model invariants:

1. cache mode never creates durable recovery claims;
2. deletion/purge sets are subsets of model-proven-deletable objects;
3. recovered visible state equals model visible state after healthy recovery;
4. lossy recovery records degraded health before data-loss-sensitive operations;
5. checkpoint watermarks never exceed visible or recovered durable coverage;
6. WAL truncation never removes versions above the proven retention watermark;
7. table flush/compaction/materialization never changes visible read results;
8. quarantine precedes purge;
9. close rejects new mutations after close starts;
10. double close after success is idempotent.

The model does not need to reimplement L5 table encoding or L6 branch merge
rules. It should call production storage surfaces and compare only lifecycle
facts, visibility summaries, object-family summaries, and safety sets.

## Script Decoder

Use a deterministic byte script. Avoid random sources inside the contract.

Recommended shape:

1. first byte selects storage mode and strict/lossy recovery policy;
2. second byte selects initial fixture family;
3. remaining bytes decode into bounded operations;
4. every operation has a maximum row/object/task count;
5. invalid operation combinations become typed validation routes, not panics;
6. the decoder always records whether an operation was input-derived or
   canonical smoke setup.

Bounded limits:

1. maximum operations per script: 64;
2. maximum branches per script: 4;
3. maximum keys per script: 32;
4. maximum snapshots per script: 8;
5. maximum table objects per script: 32;
6. maximum maintenance queue depth: current lifecycle config limit;
7. maximum WAL records per fixture: 64.

Generated contracts must reject any assurance route that reaches every required
counter only through an unconditional canonical prelude. Canonical smoke setup
may exist, but input-derived counters must be asserted separately.

## Fault Windows

L8O adds direct fault windows where production code has an explicit boundary.

Required phase families:

1. capability validation before side effects;
2. writer guard acquired then manifest create fails;
3. manifest create visible but publish uncertain;
4. snapshot object published before manifest watermark update;
5. manifest watermark update before WAL truncation;
6. WAL partial tail strict vs lossy recovery;
7. WAL corruption;
8. L7 replay failure;
9. L7 replay succeeds then visible publication fails;
10. table object published then L6 install fails during flush;
11. table rewrite publishes output then branch swap fails;
12. retention proof incomplete before destructive call;
13. quarantine inventory publish failure before purge;
14. purge delete succeeds then inventory/update reporting fails;
15. close quiesce timeout;
16. close WAL sync failure;
17. close manifest/final-fact failure;
18. writer guard release/reacquire behavior.

Each fault test should assert:

1. stable lifecycle error code;
2. source chain where a lower layer exists;
3. lifecycle state after failure;
4. retryability;
5. durable health/debt facts;
6. no unsafe deletion or visibility advancement.

## Crash/Reopen Harness

Localfs crash/reopen tests are needed only for durable persistence boundaries.

L8O should expand `tests/crash_recovery.rs` and testkit helpers to cover:

1. crash after WAL append before L6 visibility;
2. crash after snapshot publish before manifest update;
3. crash after manifest update before WAL truncation;
4. crash after table object publish before branch/table install;
5. crash after quarantine inventory publish before object quarantine;
6. crash after object quarantine before purge;
7. crash after close WAL sync before writer guard release if the fake/localfs
   surface can expose the boundary.

Rules:

1. slow process-level crash tests may be `#[ignore]`;
2. every ignored crash test must have a smaller non-ignored unit or integration
   test covering the same phase classification;
3. crash tests use `tests/common` temp-root helpers;
4. no test relies on wall-clock sleeping;
5. test directory retention is controlled by the existing test environment
   helper.

## Fuzz Targets And Corpora

Add lifecycle fuzz targets under `crates/storage-next/fuzz/fuzz_targets/`.

Targets:

1. `lifecycle_recovery.rs`
   - calls `check_lifecycle_recovery_fuzz_contract(data)`;
   - decodes durable recovery fixtures;
   - corrupt bytes must produce typed error/health, not panic.

2. `lifecycle_maintenance.rs`
   - calls `check_lifecycle_maintenance_fuzz_contract(data)`;
   - decodes maintenance/flush/checkpoint/rewrite/close operations;
   - asserts task ordering and retry facts.

3. `lifecycle_retention.rs`
   - calls `check_lifecycle_retention_fuzz_contract(data)`;
   - decodes object inventories, reachability facts, recovery health, and
     quarantine/purge operations;
   - asserts destructive actions never exceed model proof.

Each target must:

1. call a distinct contract function;
2. avoid sharing a generic scaffold-only contract;
3. accept arbitrary bytes without panicking;
4. be registered in the fuzz manifest;
5. have at least three non-empty seed files in `fuzz/corpus/<target>/`;
6. include one valid seed, one corrupt/invalid seed, and one mixed-operation
   seed.

If nightly fuzzing is not available in CI, L8O still checks target registration,
distinct routing, and seed corpora with normal tests. L8P later consolidates
the final inventory.

## Source Guard Policy

The existing lifecycle source guard remains the primary boundary guard. L8O adds
assurance-specific checks:

1. lifecycle production source does not import testkit, fuzz, proptest,
   tempfile, or crash harness helpers;
2. lifecycle production source does not contain architecture slice labels in
   code/comments/fixture bytes;
3. fuzz targets call distinct contract functions;
4. fuzz corpora directories exist and contain non-empty seeds;
5. crash tests stay behind `localfs` and non-wasm feature gates;
6. ignored crash tests have a non-ignored phase-equivalent test;
7. generated contracts expose counters for each required family;
8. generated properties assert input-derived counters, not only canonical
   smoke counters.

## Implementation Steps

1. Add the lifecycle script model and operation decoder in testkit.
2. Add input-derived counters to existing lifecycle family contracts where they
   are missing.
3. Add a composed lifecycle script contract that drives several operation
   families in one run.
4. Extend `lifecycle_properties.rs` to run the composed contract and assert
   phase counters.
5. Add `lifecycle_faults.rs` with direct fault-window tests for the durable
   phase families.
6. Expand `crash_recovery.rs` and testkit localfs harnesses for durable crash
   windows.
7. Add lifecycle fuzz targets and seed corpora.
8. Extend source guards for fuzz/corpus/assurance structure.
9. Run the direct lifecycle suite and generated test suite.
10. Record shipped files, intentional changes, deferred items, sensitivity
    evidence, and verification commands in the porting log.

## Review Checklist

Before closing L8O:

1. every generated contract has model assertions and input-derived counters;
2. generated coverage cannot pass solely because of canonical prelude cases;
3. every fuzz target calls a distinct contract;
4. fuzz corpora have meaningful non-empty seeds;
5. direct fault tests cover every required phase family or record a clear
   deferral to L8P/later with reason;
6. crash tests cover durable boundaries or have a non-ignored unit equivalent;
7. source guards prevent production/testkit/fuzz boundary drift;
8. no production lifecycle code imports testkit or fuzz dependencies;
9. no L8O change exposes public lifecycle API;
10. command matrix below passes.
