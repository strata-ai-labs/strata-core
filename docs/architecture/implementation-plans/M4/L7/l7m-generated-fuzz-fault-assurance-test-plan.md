# L7M Test Plan: Generated Fuzz And Fault Assurance

Status: draft test plan

Implementation plan:
`docs/architecture/implementation-plans/M4/L7/l7m-generated-fuzz-fault-assurance-implementation-plan.md`

Parent plan:
`docs/architecture/implementation-plans/m4-l7-commit-runtime-test-plan.md`

## Goal

Prove that L7 behavior holds across generated multi-step scripts, not only
single-purpose unit examples.

The suite must fail if L7:

1. allocates versions or timestamps in the wrong phase;
2. applies rows before WAL durability in durable mode;
3. advances visible version before all intended rows and timeline rows are
   installed;
4. loses unresolved durable state after post-WAL failures;
5. accepts stale read-set or CAS facts after another visible commit;
6. lets branch lifecycle or generation checks happen after allocation;
7. lets quiesce and normal mutating branch guards overlap;
8. lets replay duplicate mismatches succeed;
9. derives timeline lookup results differently from the model;
10. leaks user value bytes in errors generated by scripted failures;
11. treats fuzz-target registration as enough without distinct behavioral
    contracts.

Do not add tests that only assert planning documents exist. L7M tests should
exercise generated storage behavior, fault phases, fuzz routing, and seed
coverage.

## Test Locations

Use these locations:

1. `crates/storage-next/src/testkit/commit_runtime_script.rs` for script decoder
   unit tests.
2. `crates/storage-next/src/testkit/commit_runtime_model.rs` for independent
   model unit tests.
3. `crates/storage-next/src/testkit/commit_runtime_runner.rs` for model-vs-real
   runner checks.
4. `crates/storage-next/src/testkit/commit_runtime_faults.rs` for fault contract
   helpers.
5. `crates/storage-next/src/testkit/commit_runtime_fuzz.rs` for fuzz contract
   entrypoints.
6. `crates/storage-next/tests/commit_runtime_properties.rs` for generated
   property tests.
7. `crates/storage-next/tests/commit_runtime_faults.rs` for direct scripted
   fault windows.
8. `crates/storage-next/fuzz/fuzz_targets/commit_runtime_*.rs` for fuzz targets.
9. `crates/storage-next/fuzz/corpus/commit_runtime_*` for seed corpora.
10. `crates/storage-next/tests/commit_runtime_source_guard.rs` for boundary
    checks if L7M adds fuzz/testkit routing guards.

## Fixture Rules

1. Use deterministic branch ids, physical keys, values, and timestamps.
2. Bound all generated sizes: branches, operations, mutations, key bytes, value
   bytes, and replay rows.
3. Prefer fake L7 trait surfaces over backend IO for commit-runtime faults.
4. Never use actual sleeps, spawned threads, async runtimes, filesystem IO, or
   wall-clock timeout behavior.
5. Keep error assertions value-free.
6. Keep model code independent of production runtime helpers.
7. Use generated scripts to cover behavior; keep direct tests for precise phase
   assertions.

## Direct Test Matrix

### 1. Script Decoder

Required cases:

1. empty input produces a deterministic no-panic result;
2. short input exercises at least one operation;
3. large input is clamped to the configured operation limit;
4. branch ids are selected from the script branch set;
5. mutation counts never exceed `CommitRuntimeConfig`;
6. key/value lengths are bounded;
7. every operation enum variant can be decoded from at least one seed fixture;
8. decoder output is deterministic for identical input bytes.

Assertions:

1. decoder never panics;
2. decoder never allocates from attacker-controlled lengths without bounds;
3. decoder does not import production commit executors.

### 2. Independent Model

Required cases:

1. cache put/delete updates model rows and visible version;
2. durable success records WAL-before-apply-before-visible order;
3. durable clean WAL failure leaves no rows and no unresolved durable gate;
4. durable uncertain WAL failure leaves no visible rows;
5. post-WAL apply failure records durable-not-applied;
6. post-apply visible failure records applied-not-visible;
7. unresolved durable state blocks cache and durable model commits;
8. replay exact duplicate is idempotent;
9. replay duplicate mismatch rejects;
10. read-only diagnostic does not allocate;
11. branch deleting/deleted/generation mismatch rejects before allocation;
12. quiesce blocks branch guards and branch guards block quiesce;
13. visible reads ignore rows above global visible version;
14. timeline lookup uses timestamp and version tiebreak.

Assertions:

1. expected results come from model state, not production runtime calls;
2. model phases map cleanly to L7 error/outcome categories;
3. model state is inspectable after every step.

### 3. Production Runner Parity

Required cases:

1. generated cache-only script matches model after every operation;
2. generated durable happy-path script matches model;
3. generated mixed cache/durable script matches model;
4. generated conflict script rejects before allocation and matches model;
5. generated branch lifecycle script matches model;
6. generated guard/quiesce script matches model;
7. generated replay script catches up allocator and visible facts;
8. generated script with invalid operations reports expected typed errors.

Assertions after each operation:

1. visible version matches;
2. allocator version floor matches;
3. timestamp floor matches;
4. unresolved durable gate state matches;
5. touched-key latest visible rows match;
6. timeline lookup results match;
7. branch lifecycle/generation facts match;
8. guard/quiesce state matches;
9. user value bytes do not appear in error display/debug strings.

### 4. Generated Property Harness

Required cases:

1. proptest scripts cover 1 to 8 branches;
2. scripts cover 0 to 64 operations;
3. cache, durable, replay, read-only, conflict, timeline, guard, and quiesce
   categories all have nonzero counters;
4. success and failure routes both appear over the default case set;
5. property failure persistence writes to a commit-runtime regression file.

Assertions:

1. `CommitRuntimeScaffoldOutcome` smoke counters remain nonzero;
2. new model-runner counters are nonzero;
3. every successful visible commit has model-production read parity;
4. every failure route reports the model-expected phase.

### 5. Fault Windows

Required fault cases:

1. timestamp source unavailable before version allocation;
2. WAL clean failure after allocation and before apply;
3. WAL writer halted before durable acknowledgment;
4. WAL segment id overflow or segment-roll failure before durable
   acknowledgment;
5. WAL uncertain failure before apply;
6. WAL durable success then L6 apply failure;
7. WAL durable success then visible publish failure;
8. cache L6 apply failure;
9. cache visible publish failure;
10. replay apply failure;
11. replay visible publish failure;
12. unresolved durable gate record failure if the fake gate surface can inject
    it without changing production code;
13. unresolved durable gate clear failure during replay if injectable.

For each case assert:

1. branch guard is released;
2. allocator gap behavior matches the phase;
3. visible version moves only in documented phases;
4. unresolved durable gate records only post-WAL durable failures;
5. later normal commits are blocked when unresolved durable state exists;
6. read-only diagnostics remain allowed where L7J permits them;
7. errors preserve lower-layer source chains when a source exists.

### 6. Fuzz Target Routing

Required cases:

1. `commit_runtime_batch.rs` calls
   `check_commit_runtime_batch_contract`;
2. `commit_runtime_conflict.rs` calls
   `check_commit_runtime_conflict_contract`;
3. `commit_runtime_durable.rs` calls
   `check_commit_runtime_durable_contract`;
4. `commit_runtime_timeline.rs` calls
   `check_commit_runtime_timeline_contract`;
5. no commit runtime fuzz target only calls
   `check_commit_runtime_scaffold_contract`;
6. fuzz targets compile with `default-features = false` and `testkit`.

Assertions:

1. target names are registered in `fuzz/Cargo.toml`;
2. target files exist;
3. target routing is distinct;
4. target bodies are small and do not duplicate large contract logic.

### 7. Fuzz Seed Corpora

Required directories:

1. `fuzz/corpus/commit_runtime_batch`
2. `fuzz/corpus/commit_runtime_conflict`
3. `fuzz/corpus/commit_runtime_durable`
4. `fuzz/corpus/commit_runtime_timeline`

Required seed themes:

1. cache put/delete;
2. stale read-set conflict;
3. stale CAS conflict;
4. durable clean WAL failure;
5. durable uncertain WAL failure;
6. post-WAL L6 apply failure;
7. visible publication failure;
8. replay exact duplicate;
9. replay duplicate mismatch;
10. duplicate timestamp timeline tiebreak;
11. quiesce and branch-guard contention.

Assertions:

1. each directory has at least two non-empty seeds;
2. at least one seed in each directory reaches a success route;
3. at least one seed in each directory reaches a rejection or fault route;
4. seed bytes are stable and checked in.

### 8. Contract Entry Points

Required testkit functions:

```text
check_commit_runtime_script_contract(data)
check_commit_runtime_batch_contract(data)
check_commit_runtime_conflict_contract(data)
check_commit_runtime_durable_contract(data)
check_commit_runtime_timeline_contract(data)
check_commit_runtime_fault_contract(data)
```

Assertions:

1. each function returns a structured outcome or typed testkit error;
2. each function is deterministic for identical input;
3. each function enforces bounds before constructing rows or values;
4. each function increments counters that property tests can assert.

### 9. Source Boundary

Required checks:

1. production `src/commit/` still has no public transaction/session API;
2. production `src/commit/` still has no backend/layout/filesystem imports;
3. production `src/commit/` still has no product vocabulary;
4. testkit/fuzz code imports commit internals only behind `testkit` or test
   targets;
5. fuzz target files do not import backend or filesystem APIs directly;
6. generated tests do not introduce sleeps, async runtimes, or wall-clock waits.

## Property Coverage Targets

The generated harness should expose and assert counters for:

1. decoded scripts;
2. decoded operations by kind;
3. cache success/failure;
4. durable success/failure;
5. replay success/failure;
6. read-only diagnostics;
7. conflict rejections;
8. branch lifecycle rejections;
9. guard/quiesce rejections;
10. fault windows by phase;
11. timeline lookups;
12. visible read parity checks;
13. model-production parity checks.

The default property test should keep local runtime reasonable. If 64 cases are
too expensive after real scripts land, use fewer default cases and add one
larger ignored/stress test.

## Sensitivity Coverage Hand-Off

L7M should create enough generated/fault coverage for L7N to record mutation
probes. L7M itself should not fake the final ledger.

Mutation categories that L7M coverage should be able to catch:

1. allocate before admission;
2. validate conflicts after allocation;
3. apply before WAL append in durable mode;
4. publish visible before timeline rows install;
5. ignore unresolved durable gate;
6. treat post-WAL failure as clean rejection;
7. replay duplicate mismatch as idempotent;
8. sort timeline duplicate timestamps in the wrong version order;
9. allow quiesce and branch guard overlap;
10. leak user value bytes into generated fault errors.

## Commands

Minimum commands after implementing L7M:

```bash
cargo fmt --package strata-storage-next --check
cargo test -p strata-storage-next --locked --lib commit
cargo test -p strata-storage-next --locked --test commit_runtime_properties
cargo test -p strata-storage-next --all-features --locked --test commit_runtime_faults
cargo test -p strata-storage-next --locked --test commit_runtime_source_guard
cargo test -p strata-storage-next --no-default-features --locked --lib commit
cargo check -p strata-storage-next --no-default-features --target wasm32-unknown-unknown --all-targets --locked
cargo clippy -p strata-storage-next --all-targets --all-features --locked -- -D warnings
git diff --check
```

Optional when nightly/libfuzzer is available:

```bash
cargo +nightly fuzz run commit_runtime_batch -- -max_total_time=60
cargo +nightly fuzz run commit_runtime_conflict -- -max_total_time=60
cargo +nightly fuzz run commit_runtime_durable -- -max_total_time=60
cargo +nightly fuzz run commit_runtime_timeline -- -max_total_time=60
```

If nightly fuzzing is unavailable, L7M must still prove target registration,
distinct contract routing, and checked-in seed corpora through normal tests or
source guards.

## Exit Gate

L7M is complete when:

1. generated scripts compare production behavior against an independent model;
2. property tests assert generated coverage counters and model parity;
3. fault tests execute phase-specific protocol failures;
4. fuzz targets are registered and call distinct contracts;
5. seed corpora exist and cover success plus failure routes;
6. source guards still pass;
7. runtime behavior remains crate-private and storage-shaped;
8. L7N has enough evidence to perform final closeout without inventing new
   behavior tests.
