# Executor-Next Command Layer Review — July 2026

**Scope:** `crates/executor-next` (103 `Command` variants, protocol DTOs, error boundary, metadata/IDL tooling, session model) and its fitness as the single standardized command layer for every downstream consumer: `cli-next`, the V1 Python SDK, the V1 Node SDK, and the V1 MCP server (`strata mcp serve`).
**Method:** 12 parallel dimension auditors (consumer parity × 5, design quality × 3, contract conformance × 4), each grounded in the executor charter (`docs/executor/executor-charter.md`), the V1 error contract, and CLAUDE.md hard rules. The old Python/Node/MCP surfaces in their sibling repos were used as *requirement sets* (evidence of what real consumers shipped), filtered against the V1-removed feature list. Every critical/high finding was adversarially re-verified by an independent default-reject agent that re-read the cited code.
**Findings:** 124 total — 3 critical, 41 high, 54 medium, 26 low. All 44 critical/high findings were verified: **17 confirmed, 21 downgraded, 6 rejected**. Medium/low findings are reported unverified.

**Status: findings report only — no fixes are made by this document.**

---

## Verdict

The executor core is genuinely well-engineered and honors its charter: `dispatch.rs` is a pure policy-free match, all 68 facade methods are provably lossless single-command wrappers, the error boundary is the strongest surface in the crate (every construction site lands on a registered `<class>.<area>.<detail>` code), and the wire format is disciplined (internally tagged commands, `deny_unknown_fields`, test-verified unknown-field rejection). The shared vocabulary — `PageInfo`, `CommitReceipt`, `MutationEffect`, `BatchResult`, uniform branch/space addressing — is legitimately Stripe-grade design.

What keeps it from being a shippable world-class surface is **completeness for the M9 consumers**, not craftsmanship. Five structural gaps dominate: (1) **no conditional write exists anywhere** — the state primitive was deliberately removed pre-V1 in favor of `txn.cas()`, but V1 then removed public transactions too, leaving no safe read-modify-write for the product's agent-memory positioning; (2) **execution is fully serialized** — `execute` takes `&mut self` on a non-cloneable handle, so a threaded SDK or MCP server cannot run two reads concurrently; (3) **no read-only open / access mode** despite being a plan deliverable; (4) **branch merge/diff have no commands** (and no engine implementation) although V1 explicitly defines strict-refusal merge semantics; (5) the **metadata/IDL pipeline is architecturally excellent but schema-less and unconsumed** — no output schemas, nothing reads the catalog, and cli-next hand-writes a parallel clap tree with no drift guard, which is exactly how two sources of truth diverge.

A second tier of confirmed wire-quality defects will be breaking changes if not fixed before SDK cutover: `Bytes` serializes as JSON integer arrays (not base64), `KvScan` always reports a terminal page even when it truncates, `EventGetByType` duplicates `EventList`, config is read-only, graph time travel is implemented in the engine but unreachable, and Arrow vector import hardcodes the Cosine metric. All of these are cheap now and expensive after M9.

## Adjudicated cross-unit themes

Several findings were raised independently by multiple units; the adversarial verifiers sometimes split. Resolutions:

**T1 — Conditional writes (state / CAS) — REAL GAP, adjusted framing.** Three units flagged the missing state primitive (PY-1, NODE-1, MCP-2). Verifiers established: state was formally removed pre-V1 (issue #1606 / PR #1861, 2026-03-24, rationale "redundant with KV+transactions and `txn.cas()`"), so the "silent removal" framing is false and PY-1/MCP-2 were rejected. But V1 *also* removed public manual transaction sessions — the documented successor — and no `put-if-absent` / `put-if-version` exists anywhere in executor-next or engine-next. NODE-1 (critical) is CONFIRMED on that residual: **no consumer can perform a safe concurrent read-modify-write.** The fix is a product decision (conditional-write options on the KV family), owned by engine semantics per the charter.

**T2 — Serialized execution — CONFIRMED (high).** NODE-11 confirmed; SESS-1 downgraded only because single-process CLI use masks it today. `execute(&mut self)` on a non-`Clone` handle means Python/Node SDKs and the MCP server serialize every operation, including pure reads. Needs an interior-mutability or handle-clone design before M9.

**T3 — Executor imports inference-next directly — REAL, downgraded (medium ×3).** ENGINE-4, THIN-1, DTO-3 all found the same thing: 13 `Inference*` commands dispatch straight into `strata-inference-next` and embed its types in the wire `Output`. CLAUDE.md rule 5 routes consumers through intelligence-next (M8). Verifiers downgraded because M8 doesn't exist yet and the dependency is transitional — but it must be re-pointed at intelligence-next when M8 lands, and the inference types must not freeze into the wire contract before then.

**T4 — `Bytes` on the JSON wire — CONFIRMED (high, ×2).** DSGN-5 and DTO-2 independently: `Bytes` serializes as an array of u8 integers in JSON output (`[104,101,...]`), no base64; the CLI reverse-engineers strings from it and JSON keys echo back as byte arrays. Human-hostile, bloats payloads ~4×, and every SDK would have to special-case it. Must be fixed before any wire consumer ships.

**T5 — Metadata model: excellent skeleton, missing organs — CONFIRMED (META-1, META-4); coverage complaints REJECTED.** The 32/103 IDL coverage (META-2, MCP-4) is documented slice sequencing, not a defect. What IS confirmed: the metadata model has **no argument/output schemas** (so MCP tool generation, SDK stubs, and `strata agents guide` — first-run design D3/D8 — cannot be generated from it), and **nothing consumes it** (cli-next hand-writes a parallel clap surface with no cross-check test). The schema gap is a model-shape decision that gets more expensive every slice it waits.

**T6 — KV bytes-only value model — NOT A DEFECT.** PY-2 and NODE-6 (both initially critical/high) were rejected with strong evidence: bytes KV + typed JSON capability is a documented deliberate V1 design (engine-kv-parity plan Design Decision 1; core-next-architecture assigns the canonical user value model to engine-next). Residual action: state the "KV is opaque bytes; use JSON for typed values" contract explicitly in consumer-facing docs so SDKs don't reinvent typed encodings.

**T7 — Planned-gap ledger.** Findings tagged with a milestone are absences with a credible planned home, judged only on whether the executor has a reviewed slot ready. Search/retrieval commands (M6 substrate, M8 stages), auto-embed surface (M8), config-write (M9), remaining IDL families (M9). The recurring recommendation: **reserve the wire shapes now** (a reviewed `Search` command signature, config-write key registry) so M8/M9 land into designed slots instead of inventing contracts late.

- **Severity:** **critical**  |  **Category:** missing-core-operation  |  **Unit:** NODE (Node SDK parity)
- **Evidence:** ~/Documents/GitHub/strata-nodesdk/stratadb.d.ts:706-716 defines StateNamespace with `cas(cell, newValue, {expectedVersion})` and `init(cell, value)`. ### CLI-4 — Session-default ownership is split between executor (branch) and CLI (space); --space is silently ignored by `command run`

- **Severity:** **high**  |  **Category:** session-model  |  **Unit:** CLI (CLI parity and thinness)
- **Evidence:** Executor session state is only `default_branch` (executor/mod.rs:167,208-219); space defaults per-command via DEFAULT_SPACE (input_common.rs:12). CLI injects scope.space into every verb-built Command (lib.rs, e.g. 267-268) but `command run` deserializes raw JSON untouched (lib.rs:855-885), so `strata --space app command run --command-json '{"type":"kv_put",...}'` writes to `default` while `strata --space app kv put ...` writes to `app`. REPL `use` mutates only CLI CommandContext (repl.rs:92-107), never the executor default.
- **Consumer impact:** Charter §2 assigns branch AND space session context to the executor; instead every frontend (CLI today, SDKs/MCP tomorrow) must reimplement space-default injection, and CLI users hit a silent wrong-space write when combining --space with the canonical structured entrypoint.
- **Recommendation:** Add `with_default_space`/session-scope to the executor and have the CLI (including `command run`) rely on executor-resolved defaults instead of per-command injection; at minimum error when --space is combined with `command run`.

<details><summary>Adversarial verification</summary>

**Verdict: CONFIRMED**

I independently verified every cited location: executor session state holds only default_branch (executor/mod.rs:167, 208-219) with no space analog; space defaults per-command to DEFAULT_SPACE via product_space (input_common.rs:12) and Command's space fields are Option with serde(default). The CLI applies --branch to the executor via with_default_branch (lib.rs:74-77) but injects --space only into verb-built commands, while `command run` (lib.rs:143, 855-885) deserializes raw JSON with no scope applied — so `--space app command run` with space-less JSON silently writes to `default`, and REPL `use` (repl.rs:92-107) mutates only the CLI context. The executor charter §2 explicitly assigns branch context, space context, and current-session defaults to the executor, so the recommendation aligns with the charter rather than contradicting it, and spaces/command-run are not on the V1-removed list. The impact is a real silent wrong-space write on the canonical structured entrypoint plus a charter-violating split that every future frontend must re-solve, so high severity holds.

### DSGN-5 — Bytes serialize as JSON integer arrays on the wire; JSON document keys are echoed back as Bytes; the reference CLI decodes them with a lossy heuristic

### EVOL — Wire evolution and versioning

- **EVOL-4** (medium, api-stability) — **Zero #[non_exhaustive] in executor-next; ExecutorErrorClass violates hard rule 28 and all wire enums are exhaustive.** Rust-level consumers — the PyO3 and Node FFI bridge crates that must match on Output/ExecutorErrorClass — break at compile time on every additive variant, turning each v1.1 addition into a coordinated breaking release; ExecutorErrorClass is a literal violation of CLAUDE.md hard rule 28.
  - Evidence: grep -rn non_exhaustive crates/executor-next/src/ matches only a Debug finish_non_exhaustive() (error.rs:62); ExecutorErrorClass at error.rs:130 is a public Serialize/Deserialize error enum without the attribute; Command (command.rs:21), Output (output.rs:19) and ~19 public wire enums (BatchStatus, MutationEffectKind, AdminHealthStatus, BranchStatus, GraphDirection, ...) are all exhaustive
  - Recommendation: Add #[non_exhaustive] to ExecutorErrorClass (rule 28) now, and decide explicitly (in the EVOL-3 playbook) which wire enums — at minimum Output and status/kind enums — take #[non_exhaustive] before SDK FFI crates are cut, since adding it later is itself breaking.
- **EVOL-5** (medium, sdk-generation) *(planned: EX5-EX7 (executor plan tail))* — **IDL overlay and request fixtures cover only 32 of 103 commands.** The IDL is the designated substrate for SDK/MCP/docs generation (it carries mcp_name, cli_path, per-command fixtures, errors), so Python/Node SDK and MCP tool codegen cannot be driven from it for ~70% of the surface — json, event, graph, branch, space, admin, arrow, and inference families have no authored contract entries or request goldens.
  - Evidence: crates/executor-next/idl/v1/commands/ contains only kv.yaml (13 ids) and vector.yaml (19 ids); tests/fixtures/requests/v1/ has only kv and vector dirs, while responses/v1/ covers 14 families (83 fixtures)
  - Recommendation: Finish authoring IDL command entries and request fixtures for the remaining families before SDK codegen starts; treat the command-index generator as the single source for SDK stubs and MCP tool schemas.
- **EVOL-6** (medium, wire-ownership) — **Inference Output variants embed strata-inference-next types, putting part of the wire outside the executor's contract governance.** A serde change inside strata-inference-next silently changes the executor wire that SDKs and the MCP escape hatch depend on, bypassing the golden-fixture/IDL regime that protects every other family; feature-gating also means the command vocabulary differs per build, discoverable only via the AdminCapabilities.inference boolean.
  - Evidence: output.rs:496-536 — InferenceModels/InferenceGeneration/InferenceEmbeddings etc. carry strata_inference_next::{ModelInfo, GenerateResponse, EmbedResponse, RankResponse, ModelCacheStatus} directly under #[cfg(feature = "inference")]
  - Recommendation: Either mirror these payloads into executor-owned DTOs (like every other family) or pin them with executor golden fixtures and an explicit note that inference-next's response types are frozen wire contracts; keep the capability flag as the documented probe for feature-gated vocabulary.
- **EVOL-7** (medium, newtype-stability) — **Bytes newtype deviates from hard rule 35 (no repr(transparent)/serde(transparent)) without documentation or guard.** The deviation is deliberate (serde(transparent) conflicts with the serde_bytes field attr) but unrecorded, so a future 'rule-35 cleanup' could silently flip the KV key/value wire encoding from number-array to plain array/string and break every pinned SDK; FFI consumers of ExecutorError lack the repr guarantee rule 35 promises.
  - Evidence: types/common.rs:11 `pub struct Bytes(#[serde(with = "serde_bytes")] Vec<u8>);` — neither attribute; JSON wire shape is an array of numbers (tests/command_contract/shapes.rs:20 asserts json!([110,101,119])); ExecutorError (error.rs:354) has serde(transparent) but not repr(transparent)
  - Recommendation: Add a rationale comment on Bytes stating the rule-35 exemption and that the number-array JSON shape is frozen (it is already golden-tested — reference the fixture), and add #[repr(transparent)] to ExecutorError.
- **EVOL-8** (low, forward-compat) — **No unknown-variant tolerance story for clients decoding Output from a newer binary.** A pinned v1.0 SDK talking to a v1.1 binary (e.g. system-installed strata driven over CLI JSON) hard-fails on any new output variant even for commands it never issues; embedded SDKs that version-lock the binary are safe, which is why this is low rather than high.
  - Evidence: output.rs:19 adjacently tagged enum with no #[serde(other)] catch-all; unknown `type` tag is a hard deserialize error; no documented SDK posture for tolerating new output variants
  - Recommendation: Document in the EVOL-3 playbook that generated SDK decoders must treat unknown output `type` tags as a typed 'unrecognized output (upgrade client)' result rather than a parse panic, and consider guaranteeing new outputs are only ever returned for new commands.

### ERR — Error boundary

- **ERR-3** (medium, duplicate-surface) — **Second lossy class taxonomy (ExecutorErrorClass) lives on the same error with no deletion condition.** SDK authors (Python/Node) binding the error surface must choose between two class enums; picking class() silently mislabels an access-denied or quota error as 'unavailable', producing wrong retry behavior in consumer code. Nothing marks the legacy enum transitional.
  - Evidence: crates/executor-next/src/error.rs:128-149 defines legacy ExecutorErrorClass alongside public ErrorClass; executor_class_for_status (error.rs:751-760) collapses AccessDenied | Unsupported | ResourceExhausted | Io | FailedPrecondition all into ExecutorErrorClass::Unavailable. Both class() and public_class() are pub on ExecutorError. CLAUDE.md rule 8: no two public surfaces for the same behavior; PR discipline requires transitional paths to carry a deletion condition.
  - Recommendation: Mark ExecutorErrorClass and ExecutorError::class() deprecated/transitional with an explicit deletion slice before M9B rename, or delete now — every in-repo consumer can use public_class().
- **ERR-4** (medium, hint-rendering) — **CLI human output drops hint, docs_url, and suggested_fix that the registry already provides (first-run 7.2).** CLI users and agents driving the CLI in human mode get no actionable next step on failure — the entire 'errors that teach' P4 pillar is unshipped on the highest-traffic channel even though executor-next supplies everything. JSON channel is complete, so SDK/MCP consumers are unaffected.

- **ERR-5** (low, hint-rendering) — **Default ref URL shape and domain diverge from the decided stable-slug format.** Every consumer bakes strata.dev anchor-style URLs into logs, test fixtures (tests/error_and_guards.rs:129 asserts the strata.dev URL), and user-visible errors; changing the domain later churns fixtures and any cached agent knowledge.

- **ERR-6** (low, correctness) — **RetryPolicy::Never is used as an 'unset' sentinel, so a deliberate Never can be silently upgraded to retryable.** An SDK or IPC layer proxying an ErrorStatus through executor types can observe the retry policy flip from never to retryable, causing a client to retry an operation the producer explicitly marked non-retryable.
  - Evidence: crates/executor-next/src/error.rs:654-662 override_retry_policy replaces supplied Never with the registry default; ExecutorError::from_status re-normalizes deserialized statuses (error.rs:400-404), so a wire status carrying retry_policy=never for a code whose registry default is same_request/after_state_change is mutated on ingest — round-trip is not identity.
  - Recommendation: Use Option<RetryPolicy> (or a distinct Unset marker) for 'defer to registry' instead of overloading Never; only apply the registry default when the caller supplied nothing.
- **ERR-7** (low, registry-hygiene) — **Executor registry has dead entries and no reverse-completeness test; fallback code name diverges from the contract.** Dead registry entries surface in `strata agents errors` style dumps and generated docs as codes no consumer can ever trigger; the contract/code name mismatch means anyone implementing against the contract doc matches on the wrong internal fallback code.

- **ERR-8** (low, hint-quality) — **Layout-error hints instruct users to 'run the required migration' — tooling V1 explicitly does not ship.** A first-run user or agent hitting a pre-V1 database follows the hint to a nonexistent migration command and dead-ends — the exact failure mode the errors-that-teach design exists to prevent, surfaced verbatim through CLI, Python, Node, and MCP.

### THIN — Charter conformance (thinness / one model)

- **THIN-3** (medium, split-authority) — **KV/JSON mutation effects fabricated by non-atomic executor pre-reads; engine owns the same fact for vectors.** SDK/MCP consumers displaying created-vs-updated can receive a wrong effect whenever another writer lands between the exists probe and the write; JSON batch set pays N+1 engine reads on a hot path. Two different authorities own the same product fact depending on family (CLAUDE rule 7).
  - Evidence: kv.rs:21-23 'let effect = upsert_effect(service.exists(&key)?); let outcome = service.put(...)'; kv.rs:150-155 batch_exists then put_batch; json.rs:27-28 same for set; json.rs:110-127 per-entry service.exists() inside the batch-set loop (N+1 engine reads). Contrast vector.rs:121 where the engine outcome reports created() natively.
  - Recommendation: Have engine KV put/put_batch and JSON set/batch_set_or_create return created/updated in their outcomes (as vector upsert already does) and delete the executor pre-reads.
- **THIN-4** (medium, one-canonical-path) — **Executor reimplements pagination and flips output shape for KvList.** Node/Python SDKs must union-handle two output variants for one command; time-travel listing loads the entire keyspace into executor memory; executor-side cursor semantics can drift from engine list_page semantics since two implementations own paging.
  - Evidence: batch.rs:9-39 page_or_keys materializes the full key list then filters 'key.as_bytes() > cursor.as_bytes()' and truncates; used for as_of (kv.rs:77-79) and cursor-without-limit (kv.rs:89-92) while engine list_page (kv.rs:83) serves only limit-without-as_of. Same command returns Output::Keys or Output::KeysPage depending on argument presence (kv.rs:84-96).
  - Recommendation: Add engine list_page_at (as_of-aware paging) so the executor always delegates, and collapse KvList to a single paged output variant.
- **THIN-5** (medium, consistency) — **Default list-limit policy diverges by family: JSON/vector/graph silently truncate at 100, KV is unbounded.** An MCP tool or SDK iterating JsonList without a limit silently sees at most 100 documents (page.has_more must be checked) while the identical KvList call returns everything — an executor-invented, family-divergent default that surprises consumers building generic listing code.
  - Evidence: mod.rs:93-95 DEFAULT_JSON_LIST_LIMIT/DEFAULT_VECTOR_LIST_LIMIT/DEFAULT_GRAPH_LIST_LIMIT = 100; json.rs:236 'optional_limit(limit)?.unwrap_or(DEFAULT_JSON_LIST_LIMIT)'; kv.rs:89-96 KvList with no limit returns the full key list.
  - Recommendation: Pick one policy (default page size everywhere, applied uniformly) and document it on the Command variants; the default constant should ideally come from one place, not three per-family constants.
- **THIN-6** (medium, one-canonical-path) — **create_branch_from_head is a second public path that bypasses execute().** Violates the charter's one-public-model rule (rewrite rule 4) and CLAUDE rule 8: a Rust caller has a richer/different path than the command surface for the same operation, and it skips dispatch-level branch-name/session handling that execute() applies.
  - Evidence: mod.rs:228-239: pub fn create_branch_from_head calls 'self.database.branches()?; branches.fork_current(&source, branch)?' directly, duplicating Command::BranchForkCurrent and facade::branch_fork_current, and discards the fork outcome. Sole consumer: executor-next/tests/kv_behavior.rs:170.
  - Recommendation: Delete it and port the one test to execute(Command::BranchForkCurrent) or the existing facade method.
- **THIN-7** (medium, consistency) — **KV-only duplicate-key batch rejection is executor-invented policy inconsistent across families.** SDK authors writing generic batch helpers get three different duplicate semantics: KV hard-fails the entire batch, JSON last-write-wins with synthesized effects, vector is engine-defined. Nothing in the output contract explains why.
  - Evidence: batch.rs:262-283 reject_duplicate_bytes fails the WHOLE command with 'invalid_argument.executor.kv_batch_duplicate_key'; applied only at kv.rs:142 (batch put) and kv.rs:222 (batch delete). JSON batch set instead tolerates duplicates and fakes effects via a written_docs BTreeSet (json.rs:109,121-122); vector batch upsert allows duplicates with no special handling.
  - Recommendation: Decide one duplicate policy (per-item rejection fits the Itemwise contract better than whole-command failure) and apply it to every batch family, or move duplicate semantics into the engine batch APIs.
- **THIN-8** (medium, split-authority) — **Vector batch paths duplicate engine semantic validation with executor-owned error codes.** Consumers asserting on error codes (as the V1 contract requires) see different codes for the same dimension-mismatch or missing-collection failure depending on whether they used the single or batch command; there is also a TOCTOU between the info pre-read and the batch write.
  - Evidence: vector.rs:358-374 batch upsert pre-fetches collection info and rejects per-item dimension mismatch with 'invalid_argument.executor.vector_dimension' (vector_convert.rs:131-136); vector.rs:416,454 batch get/delete pre-check 'not_found.executor.vector_collection'. Single-item upsert (vector.rs:101-123) performs no such pre-check and surfaces the engine's own error for the identical failure.
  - Recommendation: Let the engine batch APIs report per-item dimension/collection errors and pass them through, so one authority produces one code for one failure.
- **THIN-9** (low, contract-documentation) — **Itemwise BatchMode contract does not state that engine-application failure aborts the whole command.** An SDK cannot tell from the contract whether a returned error means nothing was applied (KV/JSON/vector) or whether it should have inspected per-item results (Event); retry logic written against one family is subtly wrong for another.
  - Evidence: types/common.rs:141-143 documents Itemwise as 'Valid items are applied together while invalid items are reported'; in KV/JSON/vector the single engine batch call is '?'-propagated (e.g. kv.rs:155 'service.put_batch(engine_entries)?'), so valid items are all-or-nothing, whereas Event itemwise outcomes genuinely come per-item from the engine (event.rs:21-28).
  - Recommendation: Document on BatchMode::Itemwise that input-invalid items fail positionally while the valid subset commits atomically, and note the Event family exception, or unify by adopting the Event model everywhere.
- **THIN-10** (low, surface-growth) — **68-method facade is lossless but has effectively zero consumers and no mechanicalness guard.** No current harm — it complies with charter rewrite rule 4 — but ~900 LOC of unused pub surface is exactly the substrate the legacy Strata API regrew from, and nothing stops a future method from adding a default or a second engine call unnoticed.
  - Evidence: executor/facade/* contains 68 pub methods, every one verified as build-one-Command + self.execute (e.g. facade/kv.rs:5-16); workspace grep finds a single call site outside the facade (tests/event_behavior.rs:351); cli-next uses execute() exclusively (cli-next/src/lib.rs:110-143).
  - Recommendation: Either prune the facade to the handful of methods a real consumer needs, or add a guard test that each facade method's Output equals executing the equivalent Command, locking in mechanicalness.
- **THIN-11** (low, batch-semantics) — **Arrow import is non-atomic and discards progress counts on mid-file failure.** A CLI user whose import fails midway has partially imported data with no report of rows_imported/batches_processed, making cleanup or resume guesswork.
  - Evidence: arrow/import.rs:88-95: each record batch is committed via execute(Command::KvBatchPut)? inside the loop; an error on batch N+1 returns Err, dropping the ImportCounts accumulated for batches 1..N which remain durably committed.
  - Recommendation: On failure, return a structured error carrying the partial ImportCounts (the error contract's details vector fits this), and document that import commits per record batch.
- **THIN-12** (low, conversion-hygiene) — **Minor conversion/feature blemishes: silent usize saturation and feature-dependent arrow error identity.** Practically unreachable saturation, but it contradicts the crate's own no-silent-defaulting discipline; the arrow feature-ordering quirk means a consumer probing a non-arrow build gets a misleading input error instead of failed_precondition/unimplemented for the missing feature.
  - Evidence: kv_json_convert.rs:52-54 'u64::try_from(value).unwrap_or(u64::MAX)' silently saturates (the crate's only silent-defaulting conversion, vs input_common.rs:77-96 which errors); arrow_commands.rs:48-54 (cfg not-arrow) returns invalid_argument.executor.arrow_input_missing for a missing file BEFORE the feature-disabled error, so the error code for the same input depends on build features.
  - Recommendation: Make usize_to_u64 infallible-by-construction with a rationale comment or an expect, and return the feature-disabled error unconditionally before touching the filesystem.

- **DTO-5** (medium, boundary-validation) — **No batch-size or limit caps: unbounded Vec entries and usize::MAX default limits flow to engine.** An MCP tool or SDK caller can submit a 10M-entry batch or limit=2^63 list and the executor materializes it all in one engine commit/scan — no invalid_argument or resource_exhausted at the protocol edge, so misbehaving agent loops degrade the whole embedded process. ## Rejected findings (6)

Raised by an auditor but refuted on verification. Kept for the record — several rejections carry residual actions noted in the themes above.

### PY-1 — State cell primitive has no command family and no CAS successor *(rejected)*

- **Original severity:** critical  |  **Unit:** PY
- **Original claim:** Python SDK cannot ship db.state (10 methods incl. Snapshot.state); MCP and Node SDK state tools are equally stranded. Agent checkpointing built on state.cas optimistic concurrency has no successor: KV emulation loses init/cas semantics entirely, so concurrent agents silently race.
- **Why rejected:** The raw evidence checks out — I read ~/Documents/GitHub/strata-python/python/stratadb/__init__.py (StateNamespace with set/get/init/cas/delete/list/history/batch_set), confirmed command_variants.txt (103 variants) has zero State* entries, and confirmed engine-next's KvService (crates/engine-next/src/data/kv/service.rs) offers only unconditional put/put_batch with no CAS/init/conditional write anywhere in engine-next. However, the finding's key claim that "state is not on the V1-removed list" is false: docs/product/strata-v1-feature-inventory.md lines 1227-1228, under "Remove Or Redesign Before V1", explicitly says "State-cell as an advertised V1 primitive unless a real V1 product surface is designed and implemented", and docs/architecture/v1-test-inventory.md:114 archives statecell fixtures as "not V1 product language" — so the absence of a State command family is a documented deliberate scope decision, not a missing family. Consumer impact is not real for shipped code: the Python SDK ships against the pre-V1 architecture, V1 is a declared clean break with SDK cutover at M9, and CLAUDE.md hard rule 11 defines the V1 capabilities as KV/JSON/event/vector/graph only. The residual observation that KV lacks a conditional-write successor for CAS workflows is a product-design follow-up already governed by the feature inventory's "unless a real V1 product surface is designed" clause, not a defect in executor-next.

### PY-2 — KV commands are bytes-only; the SDK's typed value contract cannot ride the wire *(rejected)*

- **Original severity:** critical  |  **Unit:** PY
- **Original claim:** Every consumer (Python, Node, MCP, CLI) must invent a client-side encoding to preserve db.kv.put('n', 42) → get('n') == 42. Divergent encodings make data written by one consumer unreadable as typed values by another and create a second public semantic model per client, violating the charter's one-canonical-model rule.
- **Why rejected:** I verified the raw evidence holds: `Command::KvPut` carries `value: Bytes` (crates/executor-next/src/command.rs:131-142), `Bytes` is a serde_bytes Vec<u8> wrapper (types/common.rs:11), engine-next `KvValue` is byte-oriented (data/kv/types.rs), no `pub enum Value` exists in engine-next/core-next, and the old core on main had the frozen 8-variant `Value` enum. However, bytes-only KV is a documented, deliberate V1 design decision, not an unresolved contract hole: engine-kv-parity-implementation-plan.md Design Decision 1 states "Parity means operational parity, not copying the old product value model... Typed product values can be layered above byte KV later"; executor-kv-command-contract-implementation-plan.md lines 54-55 repeat this and line 214 lists typed product value semantics as explicitly out of scope; the IDL overlay documents kv.put as writing a "binary value". The finding's demanded decision has also already been made: core-next-architecture.md §User Value Model assigns the canonical value type to engine-next, with executor/CLI/SDKs consuming or re-exporting it — precluding the "divergent client-side encodings" scenario. No consumer is hurt today: the V1 SDKs are M9 work that does not yet exist, and cli-next follows the documented bytes contract, so this is planned deferred work being reported as a critical shipped defect, analogous to reporting M8-planned absence as a bug.

### NODE-6 — KV value model changed from typed JSON to opaque Bytes with no canonical encoding convention *(rejected)*

- **Original severity:** high  |  **Unit:** NODE
- **Original claim:** Each SDK must invent its own value codec (JSON.stringify? MessagePack? raw UTF-8?). A database written by the Node SDK and read by the CLI or Python SDK will not round-trip typed values unless all consumers coordinate an encoding out-of-band — contradicting 'engine owns semantics' (CLAUDE.md rule 7) by pushing value semantics into every consumer.
- **Why rejected:** The quoted evidence is accurate (KvPut takes Bytes at crates/executor-next/src/command.rs:138-141, output is KvValue(Option<Bytes>) at output.rs:111, CLI wraps raw UTF-8 via bytes() at cli-next/src/lib.rs:887-889), but the finding misattributes the design decision: engine-next itself defines KV values as opaque bytes (KvValue(Vec<u8>) at crates/engine-next/src/data/kv/types.rs:116), and the primitive-implementation-contract describes KV as "the thinnest facade over the row substrate" with only a "basic text projection where values are text-like" — typed structured values are deliberately the JSON capability's job, which the executor exposes separately (JsonValue(MaybeJsonValue)). So the executor is faithfully mirroring engine-owned semantics, exactly what CLAUDE.md rule 7 and the executor charter's thin-adapter mandate require; the recommendation to add a typed-value KV variant at the executor layer would itself violate that charter. The old Node SDK's kvPut(value: any) is pre-V1 behavior, and V1 is an explicit clean break with no compatibility shims; V1 SDKs do not ship until M9, so the cross-consumer round-trip scenario is speculative, not a shipped defect — the only live consumer (cli-next) writes and reads bytes consistently. This is a deliberate value-model change (bytes KV + typed JSON capability), not a wire-contract bug; at most a one-line note in the executor contract stating "KV values are opaque bytes; use JSON for typed values" would be a docs nicety, which does not sustain the finding.

I did verify the raw facts (no CAS/if-absent variant among executor-next's commands, no 'state' in engine-next/src/data), but the finding mischaracterizes a tracked pre-V1 product removal plus an explicitly listed V1 removal as a silent V1 regression, so the impact as reported is not real.
