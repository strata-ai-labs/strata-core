# Strata — Testing Methodology & Reliability Audit

**Date:** 2026-07-06  ·  **Scope:** the whole workspace, depth-focused on the reliability core (`storage-next`)  ·  **Branch:** `v1`
**Method:** multi-agent exhaustive audit — 15 testing dimensions judged against the embedded-DB gold standard (SQLite TH3/dbsqlfuzz/MC-DC, RocksDB db_stress+crash_test, FoundationDB deterministic simulation + Buggify). Every critical/high gap was adversarially verified against the actual code + CI config. ~50 agents, ~7.5M tokens across two runs.

> **Documentation only — nothing is being changed.** This records the methodology assessment + all gaps for a remediation pass.

## The one-paragraph verdict

Strata has built a **genuinely sophisticated, near-gold-standard reliability-testing apparatus** — a recovery oracle that proves recovered state is a prefix of acknowledged history (with negative controls that prove the oracle can fail), a FoundationDB-style deterministic-simulation harness with bit-exact seed replay, four filesystem power-loss crash models, byte-level WAL-corruption taxonomies, fault sweeps that fail every traced I/O call, and reference-model parity checks. In **design**, the core is `adequate`-to-`strong`. But the apparatus is **catastrophically under-enforced**: the single most important evidence an embedded database can offer — *that it never loses or corrupts acknowledged data across a crash* — **is compiled out of every CI run**, and CI does not even trigger on the branch where all V1 work happens. The gap between the sophistication of the machinery and the reality of what actually runs is the headline. This is very good news: most of the remediation is *wiring what already exists into CI*, not building it.

## Headline: the confirmed critical findings

The adversarial pass confirmed **6 critical facets from the workflow** — all the same root cause, independently surfaced by six different audit units — **plus 2 critical concurrency gaps** from the dedicated concurrency pass. Grouped:

### 🔴 C1 — The entire crash-recovery / power-loss / fault-injection / DST / recovery-oracle durability suite never runs in CI

The crown-jewel durability tests are gated on feature **pairs** — `all(feature="fault-injection", feature="localfs")` or `all(feature="testkit", feature="localfs")` — but `storage-next`'s `default = ["localfs"]` and `fault-injection = ["testkit"]` (not `localfs`) mean **no CI invocation ever enables the pair**: `cargo test --workspace` uses default features (compiles them out), and the `--each-feature`/powerset jobs never combine them. Empirically, ~22 tests — `crash_recovery.rs`, `crash_recovery_oracle.rs`, `fault_sweep.rs`, `simulation_faults.rs`, `simulation_smoke.rs`, `fs_persistence_models.rs` — **execute in zero CI jobs**. The guards for two *known* silent-data-loss bugs (the pinned STH-4 regressions: a NoSpace fault during a `[Checkpoint,Flush]` batch that advances the WAL-replay floor past unpublished rows, and a split-rename power loss that installs a non-prefix gap) are among them. They pass green because they never run. *Corroborated independently by: `ci-enforcement`, `coverage-completeness`, `dst-simulation`, `oracle-model`, `test-quality-determinism`, `storage-core-assessment`.*

### 🔴 C1b — CI does not trigger on the `v1` integration line at all

`ci.yml` triggers only `on: pull_request/push: branches: [develop, main]`. There is no `develop` branch, `main` is frozen for old-architecture work, and **all V1 work lands on `v1` and its feature branches**. So *every* per-PR safeguard — tests, clippy, the DAG dependency-direction guard, the frozen-format golden vectors, MSRV — is **dormant on the code under active development**. Regressions accumulate on `v1` unguarded until an eventual bang-bang promotion, where per-slice attribution is lost.

### 🔴 C2 — No exhaustive interleaving model-checking; "loom" is not actually used

Concurrency correctness has **zero** interleaving model-checking. The apparent loom usage is a false positive — every "loom" match is the substring inside `Table`**`Bloom`**`Filter`/`Probe`; there is **no `loom`/`shuttle` dependency, no `#[cfg(loom)]`, no `loom::` anywhere** in `crates/*/src`. Loom exists only in design docs as a deferred "revisit later." Meanwhile the runtime hand-tunes ~1,194 atomic-ordering sites (the lock-free `BackgroundScheduler`, the sharded block cache, compaction→reader `Arc` publication), and the flagship simulation harness **deliberately runs single-threaded** (`DeterministicInline`, no worker threads) — so the shipped *threaded* runtime's concurrent commit×compaction×flush×read data-race surface is validated only by manual reasoning + a handful of timing-dependent, single-shot, x86-only stress tests.

### 🔴 C3 — No ThreadSanitizer, ASAN, or miri anywhere in CI

`ci.yml` has no `RUSTFLAGS=-Zsanitizer`, no `cargo miri`, no ARM runner. Any data race, use-after-free in the FFI/mmap unsafe, or weak-memory reordering that does not *deterministically* corrupt on this specific x86 run passes green. For a database that ships to ARM/edge (an explicit target) with hand-rolled atomics and `unsafe` FFI, this is the backstop the whole industry relies on — and it is absent.

### 🔴 CRITICAL

**`ci-enforcement` · ci-enforcement — CI does not trigger on the active V1 integration line — per-PR gate is dormant**
- *Area:* .github/workflows/ci.yml (triggers)
- *Evidence:* ci.yml:4-7 sets `on: pull_request: branches: [develop, main]` and `push: branches: [develop, main]`. `git branch -r` shows `origin/HEAD -> origin/main` and NO `origin/develop`; per CLAUDE.md `main` is frozen for old-architecture work and all V1 work happens on `v1` (integration line) and feature branches (`v1-billion-scale-perf`, `v1b-epic5-*`, etc.). A PR from a v1 feature branch targets base `v1`, which is not in [develop, main], so the pull_request filter never matches; a push to any `v1*` branch is likewise ignored. The only matching branch (`main`) contains frozen pre-V1 code. Net: fmt, clippy, cargo-deny, DAG-guard, `cargo test --workspace`, feature-matrix, MSRV, and release build never run against the storage-next/engine-next code actually being written.
- *Reliability impact:* Every other per-PR safeguard is inert on the code under development. A slice that breaks WAL fsync-halt (Rule #12), the frozen durable format golden vectors (Rule #13), recovery, or the DAG dependency direction can merge into the v1 line with no automated check. Corruption/data-loss regressions land unguarded until the eventual bang-bang v1→main promotion (M9B), where per-slice attribution and bisection are lost. This single mis-scoped trigger nullifies the entire 'what runs per-PR' story the audit assumes.
- *Remediation:* Add the integration line and its feature-branch namespace to the triggers: `branches: [v1, 'v1*', develop, main]` (or trigger on all branches for push and use base-branch filtering appropriately). Verify with a no-op PR into `v1` that all jobs execute. Make the required-status-checks branch-protection rule apply to `v1`.

**`ci-enforcement` · ci-enforcement — 28 structure-aware fuzz targets exist but no CI or OSS-Fuzz job ever runs them**

- *Remediation:* Add a CI job `cargo test -p strata-inference-next --features local` that (a) unconditionally runs the host-only unit tests — struct size/align assertions, tokenize/detokenize round-trips, path_to_cstring — with no #[ignore] and no model needed, and (b) checks in a tiny (few-MB) GGUF fixture and runs embed/embed_batch/generate/rank end-to-end so the raw-pointer and from_raw_parts paths actually execute. Wire the struct-layout assertions to fail the build so a submodule bump that changes layout is caught at PR time.

**`memory-safety` · missing-technique — No ASAN/TSAN, and hand-asserted Send/Sync FFI claims are never concurrency-tested**
- *Area:* inference-next unsafe impls
- *Evidence:* crates/inference-next/src/llama/context.rs:30-31 `// SAFETY: LlamaCppContext is only accessed through Mutex in the engine layer.` + `unsafe impl Send for LlamaCppContext {}`; crates/inference-next/src/llama/ffi.rs:277-281 `// SAFETY: llama.cpp's C API functions are thread-safe for separate contexts...` + `unsafe impl Send for LlamaCppApi {}` / `unsafe impl Sync for LlamaCppApi {}`. No test exercises concurrent access to a context or to the shared global backend (llama_backend_init via a process-global Once, ffi.rs:288). No sanitizer runs anywhere in the repo: the only ASAN/UBSAN/TSAN references are in vendored, non-executed crates/inference/vendor/llama.cpp/.github/workflows/server.yml (which itself marks THREAD as broken). ci.yml has no sanitizer job.
- *Reliability impact:* If the Mutex-per-context discipline is ever violated (a future engine change shares a context across threads, or two contexts race on llama.cpp global state), the result is a data race — undefined behaviour that can corrupt embedding/generation output or crash the process, with no test able to detect it. - *Remediation:* Add a nightly ASAN job building `--features local -Zsanitizer=address` that runs the GGUF-fixture embed/generate/rank paths plus a concurrent-embed stress test (N threads issuing embed() through the engine's Mutex path). Add a TSAN job for the same concurrency test, or model the Mutex-guarded context lifecycle with loom to prove the Send-only invariant. Document precisely which llama.cpp calls are safe cross-context vs must-be-serialized.

**`oracle-model` · weak-coverage — Post-recovery verification checks only latest state; MVCC time-travel/version/history is never oracle-diffed after a crash**
- *Area:* recovery_oracle/verify.rs scan_recovered + classify_recovered
- *Evidence:* verify.rs:58-96 scan_recovered issues a single PrefixScanReadRequest with ReadBound::Latest and drops tombstones; RecoveredState is (space,key)->(value,version) at latest only. classify_recovered compares against model.live_state_at (latest fold). The in-process temporal checks (commit_runtime_runner.rs:810 compare_timeline; engine temporal_timeline_model.rs) never cross a durable crash boundary.

## Unverified gaps (medium/low — auditor-reported, not adversarially re-checked)

### `ci-enforcement`
- **🟡 MEDIUM · ci-enforcement — No sanitizers (ASAN/TSAN) and no loom — concurrency has no data-race detector or model-checker in CI**  
  A data race or incorrect lock ordering in the commit-vs-maintenance path (e.g., a torn read of the branch/LSM manifest, a lost update under concurrent commit) has no automated detector. The deterministic simulation harness varies schedules but is single-process and cannot catch true C-level/atomic data races the way TSAN can, nor exhaustively enumerate interleavings the way loom does for lock-free code. Concurrency corruption could reach production undetected.  
  *Fix:* Add a TSAN job (`RUSTFLAGS=-Zsanitizer=thread cargo +nightly test`) over the fault/DST features, and adopt loom for any lock-free/atomic sequencing in the commit and manifest-install paths with a dedicated `cfg(loom)` test job.
- **🟡 MEDIUM · ci-enforcement — No miri job for UB/provenance on FFI/mmap unsafe and codec logic**  
  Undefined behavior — misaligned reads, invalid provenance, out-of-bounds in the mmap/reinterpret paths, or UB in serde/codec — can produce silently wrong reads or corruption that is invisible on the CI platform but manifests on another architecture or optimization level. miri is the standard net for exactly these, and it runs nowhere.  
  *Fix:* Add a `cargo +nightly miri test` job scoped to the safe-Rust codec/format and recovery modules (miri cannot cross FFI, so structure the tests to exercise the pure-Rust decode paths), run at least nightly.
- **🟡 MEDIUM · ci-enforcement — No benchmark or performance-regression gate**  
  A performance regression (e.g., compaction I/O starvation, read-path amplification) can land unnoticed. More subtly, some correctness issues only manifest at scale (billion-key range scans, compaction under load) and a perf/scale harness in CI is often what surfaces them; without any continuous perf/scale run, silent-wrong-result-at-scale and latency regressions have no automated backstop.  
  *Fix:* Add a scheduled perf job that runs a fixed workload against a pinned baseline (e.g., criterion + a regression threshold, or the strata-benchmarks harness re-baselined for V1) and fails on >X% regression; include at least one large-scale scan/compaction scenario.

### `coverage-completeness`
- **🟡 MEDIUM · ci-enforcement — Fuzzing infrastructure exists but never runs in CI — not even a fuzz-once smoke gate**  
  Parser-robustness regressions in the frozen durable decoders (a decoder that panics, allocates unbounded, or accepts a malformed checksum as valid — the fail-closed contract the fuzz README states) are caught only if an engineer manually runs cargo-fuzz. A malformed/corrupt on-disk artifact reaching a regressed decoder could panic recovery or silently accept bad data. The format is frozen (CLAUDE #13), so decoder robustness is a permanent obligation the pipeline doesn't verify.

Consider onboarding to OSS-Fuzz for continuous compute.
- **🟡 MEDIUM · gold-standard-gap — Backend fault injection limited to publish/delete steps; no read/list/metadata/sync fault hooks and no OOM injection**

The publish-window classification is well covered, but the far larger read/list/recovery-read surface has no negative-path exercise — a class of real-world disk/memory failures the suite would not catch.

Add an allocator-failure harness (a global allocator wrapper that fails the Nth allocation) and assert no panic/corruption across commit and recovery.
- **🟡 MEDIUM · gold-standard-gap — No nightly/soak lane, deep bug-hunt sweep is #[ignore], and CI is single-platform (Linux only)**  
  Leaked temp files/locks, retention-debt growth, and recovery-time creep (the things only a sustained soak surfaces) go undetected. Platform-specific path/fsync/mmap behavior on macOS/Windows is unexercised. The deterministic simulator — arguably the highest-value asset here (DST-style seeded fault×crash exploration) — contributes only 16 shallow cases even in the (currently non-running, per finding 1) CI path, versus FoundationDB running thousands of seeds nightly as its primary correctness method.  
  *Fix:* Add a scheduled (nightly) workflow that runs the fault/crash simulation with a large STRATA_STORAGE_FAULT_CASES budget and the ≥1-hour mutation+retention+reopen soak, on both Linux and (at least) macOS runners. Report seed and case counts as artifacts. Raise the default CI-fast case cap once finding 1 makes the sim actually run per-PR.

### `crash-recovery`
- **🟡 MEDIUM · missing-technique — No true process-kill (or VFS-level) crash — every crash is an in-process Rust `drop`**  
  Bugs that only manifest across a real process boundary are invisible: a Drop impl on a live subsystem (e.g. commit/guard.rs, lifecycle/background.rs, commit/durable_gate.rs all impl Drop) that flushes/releases the writer lock cleanly, or page-cache state that a SIGKILL would leave half-written but the same process's reopen reads back consistently. The plain-drop zero-loss spine silently assumes no Drop path performs durability work.  
  *Fix:* Add a `std::process::Command`-spawned child harness that drives a seeded durable workload and is SIGKILL'd at seeded points, then reopens from a cold process and verifies against the same recovery oracle. This is the mechanism the how-storage-next-is-tested.md doc already claims exists as scaffolding but does not. (The reordering backend partially mitigates by truncating to the fsync boundary, so FS-model cases are robust; the plain drop path is the exposed one.)
- **🟡 MEDIUM · ci-enforcement — The exhaustive recovery-oracle sweep runs only in the dark integration target; CI covers ~4 hand-picked scenarios**  
  WAL byte-corruption swept across header/interior/tail offsets and WAL-tail truncation at every crash index — the sweep that would catch a recovery bug at an off-nominal offset or crash point — is not enforced per-PR. The representative scenarios that do run in CI are necessary but not exhaustive.  
  *Fix:* Add a bounded in-crate `#[cfg(test)]` invocation of run_recovery_oracle_harness (mirroring fault_sweep/mod.rs:523, e.g. budget 96) so the STH-1 sweep gates PRs even without the integration target, or wire the integration target into CI per finding 1.
- **🟡 MEDIUM · quality-issue — Filesystem crash model does not cover torn writes within a synced region or cross-object durability reordering**  
  A durability-ordering bug that survives the current models could hide: e.g. a torn sector inside a just-fsync'd manifest or table block (real hardware can tear at sector boundaries even post-fsync), or a multi-file inconsistency where several publishes are lost together (crash mid-batch of manifest+snapshot+table). The single-dropped-publish SplitRename only approximates the multi-file case.  
  *Fix:* Extend the FS model with (a) a torn-write mode that flips bytes inside a synced region (recovery must fail-loud via checksum), and (b) a seeded 'persistence set' mode that drops/reorders an arbitrary subset of unsynced writes and publishes across objects, all verified against the recovery oracle.
- **⚪ LOW · quality-issue — Self-assessment doc how-storage-next-is-tested.md is stale and materially inaccurate about the crash suite**  
  The doc is presented as the canonical answer to 'what does storage-next prove and where.' A reviewer relying on it gets a materially wrong picture — it both understates the coverage that exists and misstates the crash mechanism, and it never surfaces the load-bearing fact that the strong suite is not CI-enforced (finding 1). That makes it easy to over- or under-trust the substrate.  
  *Fix:* Update the doc to describe the STH-1..4 harnesses and what each proves, correct the crash mechanism to 'in-process drop + reordering FS persistence models (no real process kill),' and state the CI-enforcement boundary explicitly (which crash/fault targets run per-PR vs. require `--features testkit,fault-injection`).

### `dst-simulation`
- **🟡 MEDIUM · weak-coverage — Fault and clock/interleaving dimensions are never combined; fault taxonomy omits read faults, latency, and the silent-fsync lie**  
  A time-triggered maintenance action (size/segment-cadence checkpoint) colliding with a backend fault is never modeled, nor is an fsync that lies about durability — the exact failure CLAUDE.md rule #12 ('WAL writer halts on fsync failure') defends against. If the platform/fsync guarantee is violated, or a slow/partial write reorders visibility, the sim would not catch the resulting data loss.  
  *Fix:* Merge the dimensions: run the deterministic clock sim on a fault-capable owned backend so faults land at seeded clock-driven maintenance points. Extend FaultKind with latency, short-write/partial-write, read-op faults, and a lying-fsync mode (byte reverted after a 'successful' sync) and assert the WAL-halt contract and the recovery oracle under each.
- **🟡 MEDIUM · weak-coverage — Tiny workload and single-branch state space cannot reach compaction/multi-branch recovery paths**  
  Recovery/consistency bugs that only appear once data spans multiple compaction levels, multiple WAL segments, or several branches (cross-branch reference rejection under crash, branch generation monotonicity after recovery, compaction-output manifest torn by a crash) are unreachable by the current sweep. These are precisely the higher-scale durability failures an embedded LSM store must never exhibit.  
  *Fix:* Add seeded workload profiles that scale op counts and value sizes to force multi-level compaction and WAL rotation, and add multi-branch actions (create/commit/merge on several branches) to the sim action set, verifying the recovery oracle per branch after crash.
- **⚪ LOW · quality-issue — Determinism guard is a single hard-coded seed with no sweep-wide or CI enforcement**  
  If a future change introduces nondeterminism into a trajectory, the harness's central promise — 'any failure replays bit-exact from its printed seed' — silently breaks, turning a reproducible durability failure into a non-reproducible flake and defeating the whole point of DST as a debugging method.  
  *Fix:* Add a determinism property that runs a sample of swept seeds twice and asserts SimFacts equality, run it in the CI DST job (Finding 1), and consider hashing the full step-by-step trajectory into SimFacts so any divergence is detected structurally rather than only via the summary counters.

### `fault-injection`

Because the fault-injection integration targets never run in CI, if one bit-rots or diverges from its harness (or the process-crash harness entry breaks) CI stays green.   A real crash can lose OS page-cache writes, leave file descriptors mid-syscall, and expose partially-flushed state that a clean Rust Drop (which runs destructors and flushes buffered writers) never reproduces. - **🟡 MEDIUM · weak-coverage — Fault injection is fail-before-only at logical Backend-op granularity: no short/partial write, no mid-syscall failure, and read/list/metadata/conditional ops are never swept**  
  A write that partially lands then errors mid-flight during normal operation (e.g., ENOSPC after some bytes, an interrupted writev) can leave a torn object on disk that the next open must handle — this is never injected outside power loss. Read/list/metadata faults during recovery, compaction, or scan are not systematically swept, so a transient I/O error while reading a durable table during compaction (which could drop or duplicate rows) is only covered incidentally. This is materially short of SQLite's per-VFS-call (xRead/xWrite/xSync/xTruncate) exhaustive injection.  
  *Fix:* Add a post-op/partial-write fault mode (write N of M bytes then error; fail after the inner op with bytes present) and extend the counting sweep to ReadObject/ReadRange/ListPrefix/ObjectMetadata on the recovery and compaction paths, verified against the oracle.
- **⚪ LOW · missing-technique — No latency / delay fault injection (no FoundationDB Buggify analog)**

### `fuzzing`
- **🟡 MEDIUM · quality-issue — Format decoders fuzz for 'does not panic' only — no round-trip/idempotence oracle (except table_manifest)**  
  A codec that ACCEPTS a malformed-but-plausible durable record and silently decodes it into wrong data (mis-read length prefix, wrong field offset, checksum not enforced on a sub-field, endianness slip) passes the fuzzer because it does not panic — the classic silent-corruption class for a frozen on-disk format. Without decode→encode→decode idempotence and checksum-must-reject assertions on WAL records, snapshots, storage rows, and table blocks, such a bug survives fuzzing and manifests as wrong query results after recovery, not a crash.  
  *Fix:* For every decoder that can round-trip, assert decode(bytes)=v ⇒ encode(v) then decode again = v (byte- or value-stable), matching what table_manifest already does. Assert that flipping any byte of a valid corpus seed either still decodes to the same logical value or is rejected — never silently decodes to a DIFFERENT value (differential/mutation oracle). Assert checksum-tampered inputs are always Rejected (there is a bad-checksum corpus seed for table_manifest; extend to all checksummed formats).
- **🟡 MEDIUM · weak-coverage — End-to-end on-disk corruption is fuzzed for the WAL only — snapshots, manifests, catalogs, table artifacts are not corrupted on the recovery path**  
  CLAUDE.md #13 freezes the durable format and #12 halts the WAL on fsync failure, but recovery reads snapshots, manifests, and table artifacts too. A single-bit corruption or truncation in a snapshot or manifest that recovery mis-handles — silently dropping committed data, resurrecting a purged object, or accepting a garbage manifest and continuing — is untested end-to-end. The isolated decoder fuzzers cannot catch this because the bug is in how the recovery orchestration reacts to a decoder rejection or a plausible-but-wrong value, not in the decoder panicking.  
  *Fix:* Extend the crash-recovery oracle to a corruption sweep over ALL durable object types: for each object written by a seeded workload, apply truncation and single-/multi-byte corruption, reopen, and assert the recovery contract (fail-loud with a typed format/layout error per CLAUDE.md #42, or recover a clean prefix with no acknowledged commit lost and no phantom/resurrected object). Wire this as both an integration harness and an input-driven fuzz target.
- **🟡 MEDIUM · missing-technique — Nothing above storage-next is fuzzed — engine-next codecs, query/retrieval paths, and executor IPC have zero fuzz targets**  
  Adversarial or malformed engine-level inputs are unfuzzed: a hostile JSON document that blows up the merge, a crafted vector payload or dimension mismatch that panics the shadow-vector encoder, a derived-state manifest that decodes to an inconsistent state, or a query/scan shape that triggers a pathological cursor path. Because engine-next is the layer applications actually feed untrusted data into, a panic or silent-wrong-result there is at least as damaging as a storage decoder crash, yet it receives no fuzz coverage at all.  
  *Fix:* Add fuzz targets for engine-next codecs/decoders (JSON merge, event projection, vector/graph capability payloads, derived-state manifest, key derivation) and for the retrieval/scan cursor paths, gated behind an engine testkit surface mirroring the storage-next pattern. Prioritize the encoders that consume application-supplied bytes. Ensure they are included in the same continuous/CI fuzzing pipeline.
- **⚪ LOW · gold-standard-gap — Corpora are 2-3 hand-written seeds and non-accumulating; no minimized/coverage-built corpus is retained**  
  Even when someone runs a target locally, it starts from a near-empty corpus and must rediscover structure from scratch every time, so short local runs find little; and any interesting input a run discovers is discarded by .gitignore rather than shared, so bug-finding does not compound across contributors or CI runs. This is the opposite of the OSS-Fuzz/db_stress model where a persistent, minimized, ever-growing corpus is the primary asset.  
  *Fix:* Persist and version a minimized corpus per target (or store it as a CI cache/artifact seeded from the continuous job in finding 1), and check in reproducer inputs for any crash found. Seed corpora from the golden-vector fixtures and from real recovery-oracle-generated durable objects so the fuzzer starts near valid structure.

### `gold-standard-benchmark`
- **🟡 MEDIUM · missing-technique — No sanitizers, no Miri, no TSAN, and no per-test leak checks — UB and background-executor data races go uncaught**  
  A data race between a background compaction/checkpoint thread and the commit/publish path — the exact concurrency that mutates on-disk manifest/table state — could corrupt the durable store, and nothing in CI (which mostly exercises the deterministic inline executor) would detect it; TSAN is the standard catch. Miri would catch UB/alignment mistakes in the codec's byte reinterpretation that pass on x86 but corrupt elsewhere. RocksDB runs ASAN/TSAN/UBSAN continuously; SQLite runs valgrind + leak checks per test.  
  *Fix:* Add a Miri CI job over the unsafe-free core (codec/format/recovery pure logic), a TSAN job that runs the threaded-executor integration and background_scale/liveness tests under the real ThreadedMaintenanceExecutor, and an ASAN/UBSAN job over the FFI-adjacent (zstd/fs2) paths. Add leak assertions to long-running integration tests.
- **🟡 MEDIUM · weak-coverage — No write-ordering watchdog — WAL-sync-before-dependent-write ordering is not directly asserted (class 3 residual)**  
  This is SQLite's journal-ordering VFS invariant — 'any DB without this likely contains undetected corruption bugs.' A code change that reorders a publish ahead of its WAL sync can pass the recovery oracle on every seed whose crash point happens to miss the narrow vulnerable window, yet lose or corrupt data on real power loss when the publish reaches disk but the WAL record does not. The reordering backend perturbs unsynced writes but does not assert the ordering contract as an invariant, so the bug is only caught probabilistically, not by construction.  
  *Fix:* Wrap the Backend in a watchdog that records each object's producing-WAL-record dependency and panics if a dependent write is submitted before the corresponding fsync completes; run it across the existing durable integration workloads so the ordering contract is asserted deterministically on every commit, not just when a crash happens to land in the window.
- **🟡 MEDIUM · missing-technique — Failure-during-failure (fault injected during recovery/compaction/checkpoint) is entirely untested (class 6)**  
  Power loss frequently recurs immediately on reboot, so a crash during recovery is a realistic and dangerous case. An ENOSPC during compaction, or a second crash while replaying the WAL, can leave the store in a state that single-fault sweeps never construct — half-installed manifests, partially-rewritten tables — a concrete corruption vector. SQLite specifically tests I/O error during crash recovery; Strata does not.  
  *Fix:* Compose the existing fault backend with the recovery/compaction/checkpoint drivers: inject a fail-Nth-op fault (and a crash) while recovery/compaction/checkpoint is executing, then run the recovery oracle on the result. Sweep the injection point across the sub-operations of each maintenance phase.
- **🟡 MEDIUM · gold-standard-gap — No self-contained structural integrity check (the PRAGMA integrity_check analog) — corrupt-but-parseable databases and file-fuzzing have no cheap oracle**  
  Two gaps: (1) structure-aware DB-file fuzzing — the dbsqlfuzz signature move that mutates the on-disk file — has no cheap post-mutation oracle, so file-level corruption fuzzing can only assert 'does not panic,' not 'is internally consistent,' letting silently-wrong-but-parseable states pass. (2) There is no production/CLI self-check to detect a corrupted database before it is trusted. A manifest that references a table block that no longer exists, or a dangling delta base, could be accepted and read as if valid.  
  *Fix:* Build a self-contained verifier that walks a database directory and checks the storage invariants (manifest/table/WAL cross-references, no orphans, checksums), returning typed violations. Use it (a) as the post-mutation oracle in a new structure-aware file-fuzz target, (b) as a post-fault oracle that needs no model, and (c) as a diagnostic entry point.
- **⚪ LOW · gold-standard-gap — Frozen durable format is golden-gated on only x86-64 little-endian — no big-endian / 32-bit byte-identity verification**  
  A byte-order or width-dependent bug in the codec (e.g., a native-endian integer write, a usize-sized field) would produce a database that a differently-endian or 32-bit reader decodes as corrupt — undetectable on the LE x86-64 CI. For a format contractually frozen and intended to be portable, this is the class of silent cross-platform corruption that LMDB/redb/SQLite explicitly guard. Lower severity only because the stated near-term deployment targets are LE.  
  *Fix:* Add a CI job that runs the golden-vector tests under a big-endian target (e.g., cross to s390x or mips via `cross`) and a 32-bit target, asserting byte-identical encode/decode. If the format is intentionally LE-only, encode that as an explicit, tested assertion and document it in the format spec.
- **⚪ LOW · quality-issue — Self-assessment docs overclaim two exit bars as met (nightly soak, continuous fuzzing) and no requirements-to-test traceability exists**  
  Low direct data-loss risk, but a testing map that reads greener than the enforced reality causes future slices to be scoped as if the deep coverage is guaranteed, when in fact it only runs when a human remembers to. Without requirements-to-test traceability, an untested format-spec clause or error code is not a CI failure, so format/contract drift can go unnoticed.  
  *Fix:* Change the class 7/9 status cells to reflect that the deep/continuous runs are NOT yet automated (or, better, add the automation in finding 1 and then the cells become true). Add the requirements-to-test guard: assign stable IDs to strata-storage-format-v1 clauses and error-contract codes and a guard test that fails if any ID lacks an exercising test.

### `memory-safety`
- **🟡 MEDIUM · quality-issue — SAFETY-comment coverage is sparse and not lint-enforced**  
  The invariants each FFI call relies on (pointer non-null and validity, buffer length equals n_embd, lifetime tied to the held Mutex, correct struct layout) are undocumented for ~50 of the ~62 unsafe sites, so reviewers cannot verify them and a regression that violates one (e.g., reading emb_ptr after clear_memory, or from_raw_parts with a stale n_embd) passes review silently. This is the mechanism by which the two HIGH findings above would actually be introduced.  
  *Fix:* Enable clippy::undocumented_unsafe_blocks = "deny" scoped to inference-next (or workspace-wide as warn) and bump unsafe_op_in_unsafe_fn to deny. Backfill a SAFETY comment on every unsafe block stating the precondition and who guarantees it. Run clippy with the FFI compiled (--features local) so the lint actually sees the unsafe blocks.
- **🟡 MEDIUM · gold-standard-gap — Rule #38 unsafe-containment is not structurally enforced; no local/ module and the deny is disabled under `local` or `test`**  
  The 'audited unsafe is contained and reviewed' invariant is not machine-checked. Unsafe could be added to a pure-HTTP module (provider/openai.rs, provider/google.rs) or to any test and would compile with no warning whenever `local` or a test build is active — eroding the property that all unsafe is concentrated in one auditable FFI module and silently widening the memory-safety surface beyond what the FFI audit covers.  
  *Fix:* Move all FFI unsafe into a single local/ (or ffi/) module gated by feature=local, and apply module-level #![deny(unsafe_code)] to every other module (or add a source-guard test mirroring storage-next's *_source_guard.rs that greps for `unsafe` outside the allowed file set and fails CI). Make the deny unconditional except inside that one module so --features local and test builds still forbid stray unsafe elsewhere.
- **⚪ LOW · missing-technique — miri is absent; not run on the miri-checkable (non-FFI) pointer arithmetic**  
  Off-by-one or provenance bugs in the raw-pointer batch construction (the only intricate pointer arithmetic in the codebase) are detected by no tool; they currently rely entirely on manual review since even runtime tests of this path do not run in CI (see HIGH finding 1).  
  *Fix:* Add a miri job over a small harness that reconstructs the batch-fill loop against a Rust-allocated buffer (decoupled from the C batch_init allocation) so miri can validate the offset arithmetic and from_raw_parts length reasoning. Lower priority than the ASAN + FFI-execution jobs (which cover the real FFI) but closes the pure-Rust UB gap cheaply.

### `oracle-model`
- **🟡 MEDIUM · weak-coverage — Engine-level branch-DAG and temporal reference models run only in non-durable cache mode**  
  Branch generation monotonicity (invariant #16) and fork-equals-source-as-of correctness are proven only where nothing is persisted. If the durable path assigns generations or reconstructs the temporal index differently after a reopen, the engine-level oracles cannot see it. Confidence in durable branch/time-travel semantics rests entirely on the storage-layer oracle — which itself does not run in CI (see critical finding) and is single-branch/latest-only.  
  *Fix:* Add an engine-next proptest oracle that runs the same random branch/temporal op sequence against a durable database, forces reopen mid-sequence, and re-checks the model — bridging the engine reference model to the durability boundary.
- **🟡 MEDIUM · gold-standard-gap — No differential/reference-model oracle for engine capability semantics (JSON, graph, vector, event)**  
  The gold standard (SQLite differencing against a second SQL engine; RocksDB diffing whole logical layers) is to model-check each logical capability, not just the KV substrate. Capability-specific semantic bugs — a JSON merge that drops a field, an event projection that double-applies, a vector row that survives a delete — are only caught by whatever hand-written example happens to cover them, not by an exhaustive/randomized shadow model.  
  *Fix:* Add per-capability reference-model proptests (at minimum JSON document merge and event projection, where a small pure model is cheap) that apply a random op sequence to both the engine capability and an independent model and diff after every op, mirroring the branch/temporal model pattern.
- **🟡 MEDIUM · quality-issue — The commit-runtime model diff that runs in CI uses a fake WAL, so no end-to-end durable model diff runs on any PR**  
  Together with the critical finding, this means CI's only executed 'durable' model diff never touches a real WAL, fsync, segment file, or recovery replay. The commit protocol logic (allocation, unresolved-durable gate, replay bookkeeping) is validated, but the actual bytes-to-disk-and-back correctness — the part that determines whether committed data survives — has no executed model check on a PR.  
  *Fix:* Either (a) wire the real-WAL recovery oracle into CI (see critical finding), which is the primary fix, or (b) add a CI-runnable end-to-end commit->WAL->reopen model diff using the real localfs backend at small scope so at least one durable, real-IO model check runs per PR.
- **🟡 MEDIUM · ci-enforcement — Deep-seed soak / bug-hunt oracle runs are #[ignore], feature-gated, and have no scheduled runner**  
  The bounded CI-fast caps (96/120 cases) explore only a handful of seeds. The state of the art for durable stores is continuous randomized exploration (FoundationDB runs thousands of DST seeds nightly; RocksDB runs crash_test continuously). A recovery bug that only manifests at a rare seed/interleaving would essentially never be found, because the seed-scaling soak is never scheduled.  
  *Fix:* Add a nightly (schedule:) CI job that runs the soak/#[ignore] oracle variants with an elevated seed budget (STRATA_STORAGE_FAULT_CASES / STRATA_STORAGE_CRASH_CASES), and surface the seed on any failure (the harnesses already print the replay tuple) so failures are deterministically reproducible.

### `storage-core-assessment`
- **🟡 MEDIUM · gold-standard-gap — No coverage/MC-DC gate, no mutation testing, no Miri, no sanitizers — the discipline layer the durable core needs is entirely absent from CI**  
  Executed-but-unasserted branches (test theater) and untested cold error paths in format/WAL/recovery/commit are unmeasured — precisely where a missed branch loses data. UB/race/leak classes at the backend FFI boundary are unchecked by Miri/sanitizers.  
  *Fix:* Add an llvm-cov branch-coverage gate scoped to the durable core, a Miri job on the unsafe-free crates, an ASAN/TSAN job over the localfs backend, and a weekly cargo-mutants run with a tracked kill-rate; begin testcase!/always!/never! adoption on format/WAL/recovery/commit.
- **🟡 MEDIUM · missing-technique — Failure-during-failure (compound anomaly) testing is entirely absent**  
  An I/O error or second power-loss while the DB is replaying the WAL, materializing a branch, or compacting — a real scenario after an unclean shutdown — is untested. Compound failures are a classic double-fault corruption source that single-fault sweeps miss.  
  *Fix:* STH-5: compose the existing fault + crash harnesses to arm a backend fault at step N of recovery/compaction/checkpoint and assert the STH-1 recovery oracle still holds.
- **🟡 MEDIUM · missing-technique — No write-ordering watchdog: nothing structurally asserts a dependent publish never precedes its WAL sync**  
  A change that lets a manifest/table/snapshot publish become durable before its dependent WAL record is synced would violate WAL-before-visible and, on power loss, expose a committed-but-unlogged state. The reordering backend can model it, but no watchdog asserts the ordering, so such a regression would pass.  
  *Fix:* Implement the STH-3 slice-3b watchdog: instrument the ReorderingBackend to record sync/publish ordering per dependency and fail if any dependent publish is observed durable before its WAL segment's force-durable.
- **🟡 MEDIUM · ci-enforcement — No scheduled/nightly workflow: the deep durability soaks the docs rely on run only on manual invocation**  
  Long-tail rare-interleaving, resource-leak, retention-debt, and recovery-time-drift regressions (the class the DST is built to catch) are only caught during sporadic manual runs and can regress undetected for arbitrarily long.  
  *Fix:* Add a nightly GitHub Actions schedule job running the #[ignore] soaks with --features testkit,fault-injection and a raised seed budget, printing seeds on failure and filing issues on regression.

### `test-quality-determinism`
- **🟡 MEDIUM · missing-technique — No true out-of-process crash / power-loss testing and no OOM / allocation-failure injection**  
  In-process drop cannot reproduce failure modes that depend on real OS behavior: partially-flushed OS page cache surviving/lost across a process kill, fsync-vs-metadata durability of the directory entry, and mid-syscall interruption. OOM is a first-class real-world failure for an embedded DB pulled into a memory-constrained host (the project explicitly targets Pi Zero / edge); an unhandled allocation failure during commit or recovery could abort or leave a torn write that no current test exercises. SQLite (OOM + I/O-error injection) and RocksDB (out-of-process crash_test) both cover these.  
  *Fix:* Promote run_localfs_crash_recovery_harness to a real std::process::Command child that is SIGKILL'd at marked points, then reopen and assert the recovery-oracle prefix property. Add an allocation-failure injection lane (a failing allocator shim or a fault point on large buffer allocations in the commit/recovery path) asserting no torn write and a clean error, mirroring SQLite's OOM simulation.
- **🟡 MEDIUM · weak-coverage — Property-based tests run at a shallow default of 32 cases and only in the feature-matrix, not the primary job**  
  32 cases per property is a thin sample of the input space for invariants like key-encoding sort order, MVCC merge dedup, table-format roundtrip, and lifecycle state machines; a shrinking-discoverable counterexample that appears at, say, case 200 will not be found at 32. Because the suites also skip the primary per-PR job, a property regression is only caught in the secondary feature-matrix job, weakening the fast signal.  
  *Fix:* Raise the default enforced `cases` to a higher floor (e.g. 256) for the property suites, or drive it via `PROPTEST_CASES` in a dedicated CI step, and run the property suites in a per-PR job (they need only `testkit`, not localfs). Commit the proptest-regressions files (already present under crates/storage-next/proptest-regressions/) so any discovered counterexample is pinned and replays deterministically.
- **⚪ LOW · quality-issue — Hard Rule 29 deviation: serde-path validation errors are asserted on display prose instead of codes/classes**  
  Low direct data-integrity impact, but prose-coupled assertions are brittle: a wording change to a validation message silently breaks these tests (or, worse, a wording change that no longer contains the substring passes while the semantics changed). It normalizes a pattern the codebase otherwise forbids, and it means the serde-deserialization validation path is not pinned to a stable machine code.  
  *Fix:* Route serde-path validation through a typed error that exposes code()/class() (e.g. deserialize into the newtype and map serde failures to the same structured JsonError), then assert on the code as the direct-construction test does. If serde's opaque error truly cannot carry the code, assert only structural facts (that construction failed) plus a separate direct-construction test for the code, and drop the prose substring assertions.
- **⚪ LOW · quality-issue — Latent wall-clock timing assertions in background tests would be load-sensitive/flaky if enabled**  
  No current impact (tests do not run). But these are a latent flakiness source: if the L8G ignore is lifted without converting the timing assertion to the deterministic maintenance-clock boundary the source-guards already mandate for production code, they will intermittently fail on loaded CI runners, eroding trust in the suite and creating pressure to re-ignore rather than fix.  
  *Fix:* When these tests are un-ignored in L8H, replace wall-clock elapsed-time assertions with the injectable MaintenanceClock/MaintenanceInstant boundary that source_guards.rs:336-379 already require in the production drive logic, so the timing behavior is asserted deterministically rather than against real wall time. Keep the Instant::now watchdogs only as non-asserting failsafes.

### `upper-layer-testing`
- **🟡 MEDIUM · gold-standard-gap — No coverage measurement, MC/DC, or mutation testing anywhere in the workspace**  
  The embedded-DB gold standard (SQLite) is ~100% MC/DC branch coverage precisely because untested error/recovery branches are where silent corruption hides. With no coverage signal, unexercised temporal/tombstone/merge/restore error paths in engine-next cannot be identified, and a passing green suite gives false confidence. Mutation testing would also reveal assertion-shallow tests (e.g., conformance tests that only check `is_some()`).  
  *Fix:* Add a `cargo llvm-cov` job producing per-crate line+branch coverage with a ratcheting floor for engine-next/executor-next/core-next, and a periodic `cargo-mutants` run on the engine semantics modules (branch, temporal, persistence mapping) to validate test effectiveness.
- **🟡 MEDIUM · weak-coverage — cli-next has no integration tests — output rendering, JSON goldens, and error exit codes are untested**  
  The CLI is a primary product surface and exit codes are the automation contract. A swallowed error returning exit 0 would make user scripts believe a failed write succeeded (perceived data loss); a bug in render.rs `raw_scalar`/`bytes_from_json_array` byte decoding could silently display wrong stored values. None of this is guarded.  
  *Fix:* Add a cli-next integration test target driving the built binary (assert_cmd/trycmd) with golden fixtures for `--json` output shape, a full exit-code table across success/not-found/invalid-input/closed/write-failure, and render.rs unit tests over representative Output values including byte-array values.
- **🟡 MEDIUM · quality-issue — Advertised conformance harnesses do not exist; no cross-capability product-pathway suite**  
  Cross-capability interaction bugs (e.g., branch fork interacting with the vector index manifest, restore invalidating derived state, time-travel over a graph relationship) are never exercised end-to-end. The documented 'milestone conformance' cannot actually be run, so a reviewer trusting the command table would get a false green (command errors out or silently tests nothing).  
  *Fix:* Either build the advertised `product_pathways` engine suite covering the plan's cross-capability workflows, or correct CLAUDE.md/the plan to match reality. Fix the `format_goldens`->`format_golden` command mismatch. Do not advertise conformance harnesses that don't exist.
- **🟡 MEDIUM · weak-coverage — Property/model testing covers only 2 of 8 required models; data-critical branch merge/restore/diff are unmodeled**  
  Branch merge/restore/diff/copy are the operations most likely to lose, duplicate, or resurrect data, and they are validated only by hand-picked example tests rather than model-equivalence over generated DAGs/histories — the opposite of the FoundationDB approach where randomized model-based testing is the primary correctness method. A merge/restore edge case (concurrent divergent history, tombstone resurrection, pruned-point fork) can silently produce wrong visible data.  
  *Fix:* Add proptest model harnesses for the remaining 6 models, prioritizing branch diff/merge/copy/restore equivalence against a simple in-memory branch model and per-key history/as-of resolution, per the plan's Branch and Temporal model sections.
- **🟡 MEDIUM · weak-coverage — Persistence fault injection is narrow and runs only against non-durable cache mode**  
  The fault seam proves error-message MAPPING but never exercises how the durable localfs write path (the path that actually risks data loss) responds to injected storage faults, nor post-commit/derived-state failures. A durable-but-not-visible or post-commit-hook failure that leaves the derived-state manifest or branch metadata inconsistent would not be caught at the engine boundary.  
  *Fix:* Extend fault injection to run against durable localfs databases, add post-commit-hook and derived-state-update fault ops, and cover durable-but-not-visible on a real backend; make at least a core subset run in the default `cargo test` path rather than only under the non-default `testkit` feature.

## Dimension: property-based testing (dedicated deep pass)

MATURITY: adequate

The storage core genuinely reaches for state-of-the-art technique: model-based property tests with independent reference oracles (branch DAG generation/active-set model in `branch_dag_model.rs`, an MVCC as-of timeline oracle in `temporal_timeline_model.rs`, branch-LSM and commit-runtime reference-model *parity* harnesses including WAL fault-window invariants), plus a FoundationDB-style seeded crash-recovery oracle (`recovery_oracle/`) and a deterministic simulation (`simulation/`) that assert prefix-of-acknowledged-history, no-lost-ack/phantom/torn-batch/gap safety and queue-liveness. The pure codec round-trips that do exist (core-next atoms, table artifact, WAL commit payload) use boundary-aware generators at proptest's full 256-case default. That is well above "weak." It falls short of "unimpeachable," however, because the *strongest* harnesses are hard-capped at 16–32 cases (8–16x below proptest's own default, and unraisable via `PROPTEST_CASES` because they use struct-literal `Config { cases: 32, .. }`), most durable codecs (16 of ~17) have no randomized round-trip property — relying on golden vectors plus decode-returns-bool fuzz stubs — the MVCC key comparator's ordering invariant is a single example test, the 28 cargo-fuzz targets and the 2,000-seed simulation soak never run in CI, and every engine capability except KV (vector/graph/JSON/event) has zero property/model coverage.

### [high] ci-enforcement — Strongest property harnesses hard-capped at 16–32 cases and unraisable via env
- **Area:** Case-count budget for the storage-next model/parity harnesses (branch-LSM, commit-runtime, API read/commit/branch/maintenance/diagnostics, lifecycle).
- **Evidence:** `crates/storage-next/tests/api_properties.rs:17,89,127,163,204,242` (`cases: 32`); `commit_runtime_properties.rs:15,46` (`cases: 32`); `branch_lsm_properties.rs:430,463` (`cases: 32`); `lifecycle_properties.rs:15,46,87,128,176,216,254,298,339,381` (`cases: 16` and `32`); `api/tests/read.rs:1027` (`cases: 48`). All are `Config { cases: N, ..Config::default() }` struct literals, so a `PROPTEST_CASES` env var is overridden and cannot deepen them. CI (`ci.yml:55`) runs plain `cargo test --workspace` with no override.
- **Reliability impact:** The properties covering the most complex semantics (branch-scoped LSM compaction/snapshot parity, commit atomicity/conflict, MVCC read routing) each explore only 16–32 randomized inputs per CI run — a needle bug that surfaces at, say, 1-in-500 inputs will essentially never be sampled, so MVCC mis-reads, compaction row-loss, or conflict-detection escapes ship undetected. There is no knob to deepen them for a nightly/soak lane without editing source.
- **Remediation:** Replace the hardcoded `cases:` literals with a shared helper that reads `PROPTEST_CASES` (default e.g. 256, floor at existing values) and add a CI job (or nightly) that runs the storage suite with a raised count (e.g. `PROPTEST_CASES=4096`).

### [high] gold-standard-gap — Most durable codecs have no randomized round-trip property; robustness is decode-returns-bool only
- **Area:** Round-trip (`decode∘encode == id`) and decode-robustness for the frozen durable format (rule 13).
- **Evidence:** Only `format/table/property_tests.rs` and `format/wal/commit_payload.rs` contain proptest round-trips. `grep proptest crates/storage-next/src/format` returns exactly those two. The other ~15 codecs (`encode/decode_manifest`, `physical_key`, `internal_key`, `storage_row`, snapshot header/section/container, `wal_record`, `wal_segment_header`, `table_manifest`, `segment_metadata`, `watermark`, `pending_releases_manifest`, `retained_history_extension`, `quarantine`, `branch_catalog_manifest`, `snapshot_rows`) have only golden-vector + corruption unit tests. The `format/fuzzing.rs` "fuzz" functions (lines 6–90) merely return `decode(...).is_ok()` — no round-trip, no assertion (only `decode_table_manifest` re-encodes). The 28 cargo-fuzz targets that would exercise them are not run in CI (see next finding).
- **Reliability impact:** Golden vectors pin a handful of known-good encodings but do not prove `decode(encode(x)) == x` over the input space, so a codec that silently drops/reorders a field (e.g. a manifest table entry, a snapshot section, a storage-row expiry/TTL) for un-golden values would pass CI and corrupt the on-disk image or recover wrong data. Robustness stubs that only check `is_ok()` cannot catch a decoder that panics or produces a valid-but-wrong struct on adversarial bytes.
- **Remediation:** Add proptest round-trip properties for each codec with structure-aware generators (as `commit_payload.rs` does), plus a `decode(arbitrary_bytes)` property asserting "never panics; always a typed `FormatError`." Wire the existing `decode_format_bytes` router into a proptest loop that asserts no panic across all `FormatDecoder` variants.

### [high] ci-enforcement — 28 cargo-fuzz targets and the 2,000-seed simulation soak never run in CI
- **Area:** Continuous fuzzing / deep simulation.
- **Evidence:** `crates/storage-next/fuzz/fuzz_targets/` holds 28 libFuzzer targets (format codecs, commit-runtime, branch-LSM, lifecycle, table-runtime, service). `grep -ri 'fuzz|--ignored|nightly|schedule|soak' .github/` returns nothing — `ci.yml` has no fuzz or `--ignored` step and no scheduled job. The deep bug-hunt lane `simulation_soak_deepens_across_many_seeds` (`simulation_smoke.rs:74`) is `#[ignore]`; the CI lane runs only `case_limit … Some(16)` (`simulation_smoke.rs:41`) and the recovery oracle only `Some(96)` (`crash_recovery_oracle.rs:36`).
- **Reliability impact:** The infrastructure most capable of finding corruption/crash bugs (coverage-guided fuzzing over durable decoders, 2,000-seed crash/fault exploration) executes only when a developer remembers to run it locally. In practice regressions in decode robustness or recovery safety can merge with a green CI, because the shallow 16/96-case lanes rarely hit the fault windows the soak lane is designed to expose.
- **Remediation:** Add a scheduled (nightly/weekly) CI job that runs `cargo fuzz run` on each target for a fixed time budget and a `--ignored` soak run with a raised `STRATA_STORAGE_FAULT_CASES` / `STRATA_STORAGE_CRASH_CASES`; fail on any new crash and commit the reproducing corpus.

### [medium] gold-standard-gap — MVCC internal-key ordering (the comparator) is a single example test, not property-tested
- **Area:** `encode_internal_key` order-preservation: physical key ascending, commit version descending — the invariant the entire LSM read path relies on.
- **Evidence:** `format/key.rs:197` `internal_key_sorts_newest_version_first_for_same_key` is one hand-written unit test; there is no proptest asserting that for arbitrary `(physical_key_a, ver_a)` vs `(physical_key_b, ver_b)`, `encode(a).cmp(encode(b))` equals the semantic MVCC ordering (and that same-key newer-version sorts first via the big-endian bitwise-inverse trick at `key.rs:40`).
- **Reliability impact:** A comparator/encoding bug (e.g. version inversion wrong at a byte boundary, or physical-key prefix collisions) silently returns the wrong version on point/as-of reads and mis-orders scans — exactly the class RocksDB/FoundationDB property-test exhaustively. A single example cannot cover key-length boundaries, shared prefixes, or version boundary values.
- **Remediation:** Add a proptest generating pairs of `InternalKey` (with shared-prefix and boundary versions) asserting `encode(a).cmp(&encode(b))` matches the reference ordering, and that decode round-trips.

### [medium] weak-coverage — Capabilities beyond KV (vector, graph, JSON, event) have no property or model-based tests
- **Area:** Engine capability semantics/retrieval.
- **Evidence:** `grep -c proptest` returns 0 for `engine_vector.rs`, `engine_graph.rs`, `engine_json.rs`, `engine_event.rs`, and `capability_conformance.rs`; only `temporal_timeline_model.rs` (KV) and `branch_dag_model.rs` (branch) are model-based. Vector/graph/JSON/event are covered by example-based conformance tests only.
- **Reliability impact:** Vector search ordering/recall, graph traversal/relationship semantics, JSON document-level merge (rule 21), and event append/ordering are validated only on curated examples. Randomized model checks would catch, e.g., a vector top-k that returns wrong ordering under specific distance ties, or an event capability that violates monotonic ordering under interleaved commits — none of which curated cases reliably hit.
- **Remediation:** Add reference-oracle model tests per capability (e.g. brute-force top-k oracle for vector; a reference adjacency model for graph; a document-merge oracle for JSON) with randomized op sequences, mirroring the KV timeline oracle.

### [medium] weak-coverage — Proptest model tests run cache-mode only; durable-mode MVCC is not model-checked by proptest
- **Area:** Durable-path equivalence under the reference oracles.
- **Evidence:** `branch_dag_model.rs:217` and `temporal_timeline_model.rs:69` both `open_cache_database()`; `api_properties.rs` uses `StorageRuntime::open_ephemeral()`. Durable MVCC/recovery is checked only by the separate seeded recovery oracle (capped at 96 CI cases) and simulation (16 seeds), not by the proptest reference-model tests.
- **Reliability impact:** A semantic divergence that appears only after flush/compaction/WAL-replay on the durable backend (e.g. an as-of read that is correct in-memory but wrong after a segment is sealed) is not exercised by the strong MVCC/branch oracles, which run purely in cache mode. The durable path's equivalence to the model is asserted far more weakly.
- **Remediation:** Parameterize the branch-DAG and timeline model harnesses over {cache, durable} backends (including a flush/reopen step), so the same reference oracle runs against persisted state.

### [medium] ci-enforcement — CI triggers only on `develop`/`main`; the active v1 integration line is not in the branch filter
- **Area:** Whether proptests run at all on the branches where V1 work lands.
- **Evidence:** `ci.yml:4-7` — `pull_request: branches: [develop, main]` / `push: branches: [develop, main]`. The active line per `CLAUDE.md` is `v1` (current branch `v1-billion-scale-perf`); neither `v1*` is listed. There is no other test-running workflow (only `ci.yml` and `docs-dispatch.yml`).
- **Reliability impact:** PRs from a slice branch into the `v1` integration branch will not trigger CI, so none of the proptests/model tests run as a merge gate on the V1 line — the entire property suite's enforcement depends on an eventual `v1 → develop` merge rather than per-PR. Regressions can accumulate on `v1` unguarded.
- **Remediation:** Add the V1 integration branch(es) to the `branches:` filter (e.g. `v1`, `v1-*`), or confirm and document that all V1 PRs target `develop`.

### [low] quality-issue — Byte-script generators, coarse `Vec<u8>` shrinking, and narrow key/branch spaces limit state-space exploration
- **Area:** Generator design and shrink quality across the storage harnesses and engine models.
- **Evidence:** Storage harnesses generate `vec(any::<u8>(), 0..=N)` and decode bytes into ops inside `check_*_contract` (e.g. `api_properties.rs:97`, `branch_lsm_properties.rs:438`, `commit_runtime_properties.rs:54`); the API read model constrains to 4 keys and `take(24)` ops (`api/model.rs:88,108`). - **Reliability impact:** Proptest shrinks the raw `Vec<u8>` tape, not the decoded operation sequence, so failures shrink to still-large opaque byte vectors that are hard to diagnose, and the coarse mapping means whole regions of the op space are unreachable. - **Remediation:** Where practical, generate typed op enums with `#[derive(Arbitrary)]` / custom `Strategy` (as the format and engine models already do) instead of byte tapes, and widen the key/branch/space generators (variable-length keys, boundary versions/timestamps, larger name pools).

## Dimension: concurrency correctness (dedicated deep pass)

### [critical] missing-technique — No exhaustive interleaving model-checking despite a hand-rolled atomic scheduler

### [critical] ci-enforcement — No ThreadSanitizer (or any sanitizer/miri) job in CI
- **Area:** CI race detection.
- **Evidence:** `.github/workflows/ci.yml` — the `test` job is `cargo test --workspace` (line 55) on `ubuntu-latest` with no `RUSTFLAGS`/`-Zsanitizer`/`miri`. `grep -rin 'tsan|sanitizer|RUSTFLAGS|miri' .github/` returns nothing. - **Reliability impact:** Any data race that does not deterministically corrupt on this specific x86 run passes green. ### [high] weak-coverage — No concurrent-writer MVCC / isolation / lost-update / torn-read tests against the real runtime
- **Area:** Commit path and MVCC read visibility under real threads.
- **Evidence:** `commit/guard.rs:4` documents per-branch write serialization with independent-branch concurrency, but `grep -rn thread::spawn crates/storage-next/src/commit crates/storage-next/src/branch` is empty. - **Remediation:** Add integration tests spawning N writer + M reader threads on a real `Background` runtime asserting an accounting invariant and snapshot monotonicity across concurrent commits/compaction/flush, run in a high-iteration loop and under the TSAN job above.

### [high] gold-standard-gap — Flagship correctness harness deliberately excludes the threaded runtime
- **Area:** Seeded simulation + recovery oracle + fault sweep.
- **Evidence:** `testkit/simulation/driver.rs:1-16` — runs "under `DeterministicInline` (the production `Background` path with the inline executor + manual clock, **no worker threads**)"; the only "interleaving knob" is *when* maintenance is drained relative to commits, all on one thread (`simulation/mod.rs:4-12`). - **Reliability impact:** All of Strata's strongest coverage (property, fuzz-inventory, crash-recovery oracle) validates *logical operation ordering*, never *thread races*. The concurrency dimension is structurally absent from the very harness whose determinism makes it "unimpeachable."

### [medium] weak-coverage — Existing concurrent tests are shallow and timing-dependent
- **Area:** Block-cache and scheduler concurrent tests.
- **Evidence:** `table/tests/cache.rs:624` and `:655` spawn 8/16 threads but run **one** pass with no iteration loop and no randomized delays; scheduler tests loop 25× (`lifecycle/background.rs:1022`) but gate interleaving on `thread::sleep(50ms)` (`:1032`, `:1085`) rather than exploring schedules.
- **Reliability impact:** A rare interleaving (e.g., insert racing eviction so `bytes`/`entries` gauges diverge) rarely triggers; a green single-shot run does not imply race-freedom.
- **Remediation:** Wrap these in high-iteration loops with randomized `yield_now`/jitter, execute under the TSAN job, and/or replace with loom models where the state space is small.

### [medium] gold-standard-gap — No weak-memory (ARM/aarch64) or atomic-ordering verification
- **Area:** The ~1,194 hand-chosen atomic orderings.
- **Evidence:** `grep -c '::AcqRel|::Acquire|::Release|::Relaxed'` over non-test src = 1,194; CI is x86 `ubuntu-latest` only with no ARM matrix, no loom (which models weak memory), no miri. `docs/design/concurrency-audit-prompt.md:230` itself lists "No memory ordering tests" and flags ARM risk.
- **Reliability impact:** `Relaxed`/`AcqRel` choices that are benign under x86-TSO can reorder on aarch64 and corrupt scheduler/cache state — and aarch64 (Raspberry Pi / edge) is an explicit shipping target per project memory. This class of bug is invisible on every current CI run.
- **Remediation:** Add an `aarch64` test job (emulated or native) and/or loom/miri (both simulate weak memory) over the atomic-heavy modules; document the ordering rationale per `SchedulerInner` field as a checkable contract.
