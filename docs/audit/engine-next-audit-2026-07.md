### Verdict

engine-next is **solid where it is built** — the persistence adapter, control plane, and the capability read/write paths (KV/JSON/event/graph/vector) are implemented and largely conformant. The gaps concentrate in two places:

1. **M6 product semantics are substantially unbuilt** — the entire branch-workspace surface (compare/diff/promote/merge/copy/restore/revert/cherry-pick + the capability-branch-adapter seam), graph binding policy/target-status, and the production trigger that seals the vector index. These are contract-mandated but not yet implemented (M6 is a Planned milestone).
2. **A handful of real bugs exist in shipped code** — time-travel `as_of` read semantics (silent clamp / collapse-to-absent), graph accepting cross-branch bindings (violates Hard Rule #18), and a crash window during branch create/fork/delete that can permanently brick a durable database.

No confirmed finding is a happy-path data-loss/corruption bug; the crash-brick (E1) is the most operationally severe. Several 'high' findings are unbuilt-milestone scope rather than regressions — noted per finding.

### 2. 🟠 HIGH · `branch-commit` · correctness

**Crash between the pending-intent commit and the catalog-activation commit permanently bricks a durable database (no resume/cleanup)**

- **Location:** `crates/engine-next/src/control/bootstrap.rs:358`
- **Governing spec:** branch-operation-and-capability-adapter-contract.md — Branch Creation / Publication rule (2) and Common Workflow Shape rule 5; Conformance Tests 10 & 16

**Issue.** Every mutating branch op (create/fork/delete) runs as TWO separate durable commits: `ControlPlane::begin_branch_operation` writes a pending-index row + pending record (service.rs:65,255,304; bootstrap.rs:145-165), then a later `persist_catalog_record` / `persist_branch_record` commit activates the catalog and clears the pending rows (bootstrap.rs:185-223). If the process crashes in the window between these two commits, the pending row survives. On reopen, `load_existing_database` reads the pending index (bootstrap.rs:352-371), decodes the pending record for validation, then UNCONDITIONALLY returns `EngineError::corruption("data_loss.engine.branch_create_pending", ...)`. There is no resume-forward and no cleanup/quarantine path anywhere (grep for pending/resume/recover confirms none). The entire database — every branch, all data — becomes unopenable, and there is no repair tooling (CLAUDE.md forbids migration/repair machinery). The contract's Publication rule requires recovery to either finish publishing the branch-control rows or clean up/quarantine the destination storage state; the implementation does neither.

**Evidence.** bootstrap.rs:358-371: `if !pending_names.is_empty() { if let Some(name) = pending_names.first() { let row = read_required(...)?; let _ = decode_pending_branch_record(&row)?; } return Err(EngineError::corruption("data_loss.engine.branch_create_pending", "branch catalog contains an unfinished branch create operation")); }` — the decoded pending record is discarded (`let _ =`) and load always fails.

**Failure scenario.** Open a durable DB, call branches().create("feature"). `begin_branch_operation` fsyncs the pending rows; `persistence.create_branch` fsyncs the storage branch; process is killed before `persist_catalog_record` fsyncs. Reopen the DB: `load_existing_database` returns `data_loss.engine.branch_create_pending` and Database::open_local fails forever. All pre-existing branches (default, plus any others) are now inaccessible with no recovery path.

**Suggested fix.** Implement the contract's recovery: on load, use the persisted pending record to either (a) roll the storage branch forward by re-running catalog activation, or (b) delete/quarantine the half-created storage branch and clear the pending rows, so a crash mid-op leaves the DB openable. At minimum this must land before any durable-mode GA (M6D/M10).

<details><summary>Adversarial verification (CONFIRMED)</summary>

The code confirms every load-bearing claim.

Two separate durable commits: In `create` (branch/service.rs:59-86) the order is `ControlPlane::begin_branch_operation` (line 65) -> `persistence.create_branch` (storage fork, line 68) -> `persist_catalog_record` (line 82). `begin_branch_operation` (bootstrap.rs:145-165) does its own `persistence.commit(...)` writing the pending-index row + pending record; `persist_branch_record` (bootstrap.rs:185-223) is a distinct `persistence.commit(...)` that writes the catalog row/index AND clears the pending rows. Fork (service.rs:122, 304) and delete (service.rs:255) follow the same begin->storage->persist_catalog_record shape. So the crash window between the two fsync'd commits genuinely exists for a durable backend.

Unconditional hard fail on reopen: `load_existing_database` (bootstrap.rs:352-371) reads the pending index, and if non-empty decodes the pending record only to discard it (`let _ = decode_pending_branch_record(&row)?;`, line 365) and then UNCONDITIONALLY returns `EngineError::corruption("data_loss.engine.branch_create_pending", ...)`. This check sits at lines 352-371, BEFORE the branch-index/branch-record loading at lines 373-412, so the entire load aborts and no branches are ever loaded — every pre-existing branch and all data become unopenable.

No resume/cleanup/quarantine: grep across engine-next/src shows the only pending-clearing paths are `clear_pending_branch_operation` (bootstrap.rs:167-183) and `persist_branch_record`. Both are invoked only from the live in-process handlers `clear_pending_after_storage_error` (service.rs:363-376, runs only when create_branch returns Err in-process) and `persist_catalog_record`. Neither runs on a hard process crash, and neither is reachable from the load/recovery path. The test `pending_branch_create_fails_closed_on_load` (bootstrap.rs:473-487) codifies the brick-on-reopen behavior as intended. CLAUDE.md forbids repair/migration tooling, so there is no escape hatch — the brick is permanent.

Contract violation: Publication rule (2) (contract lines 358-361) requires that when storage fork succeeds but branch-control publication fails, recovery must EITHER finish publishing the branch-control rows OR clean up/quarantine the destination storage state before it appears as an ordinary branch. The implementation does neither — it refuses to open the whole database. Conformance Test 10 (line 820-821) is only the negative half ("cannot produce an ordinary visible branch"), which the fail-closed refusal technically satisfies, but the affirmative recovery obligation in the Publication rule is unimplemented. The pending intent is written but never consumed by recovery.

Severity: high is correct. When triggered, a single crash (or even an in-process catalog-commit failure via `fail_closed_after_branch_operation_error`, which also leaves the pending row set) during a routine branch create/fork/delete renders the entire durable database permanently unopenable with a data_loss-class error and no recovery path. Not critical because it is crash-timing-dependent rather than occurring on every run and it fails closed (refuses to open) rather than silently serving corrupt data; not medium because the blast radius is total loss of availability for the whole durable database, which is exactly the durability guarantee the store exists to provide, and the contract explicitly mandates the missing recovery path.

</details>

### 3. 🟠 HIGH · `branch-commit` · completeness

### 4. 🟠 HIGH · `event` · product-gap

**get_by_type and range_by_time/list/len_at load the entire event log into memory; the per-append type index is written on every append but never read**

- **Location:** `crates/engine-next/src/data/event/service.rs:401`
- **Governing spec:** primitive-implementation-contract.md §Event 'Query by sequence, type, range, and time'; §5 Key Encoding rule 3 (keys must support prefix/range queries needed by product APIs)

**Issue.** Every append writes a secondary type-index row (service.rs:133-136, RowClass::EventIndex, key = space|type|be(sequence)) on top of the event row and metadata row. That index is never consulted by any query — the only non-test readers of EventIndex are the space-delete cleanup path (api/space.rs:517). get_by_type_with_selector (line 390-410) answers type queries by calling event_rows -> event_raw_rows -> scan_prefix(..., None) (line 431-438), an UNBOUNDED scan of every event row in the space, then `retain`s by type. range_by_time (line 293), list_page/list (line 356), len_at (line 187), and list_types_at (line 320) do the same full-log scan (scan_prefix with limit None => read_limit maps None to unbounded, adapter.rs:895). range_by_time additionally sorts the entire log on every call (line 299). On this billion-scale branch, the core documented event operations (facade: 'append, range, range by time, list types') cannot scale, and the index that exists precisely to serve get_by_type is pure write amplification.

**Evidence.** service.rs:431 `self.persistence.scan_prefix(record.storage_branch_id(), RowClass::Event, encode_event_space_prefix(&self.space), selector, limit)` called with limit None from event_rows; service.rs:133-136 writes the EventIndex row that no query reads.

**Failure scenario.** A log with 1,000,000,000 events. `get_by_type(&EventType::new("user.created"), None, Some(10))` reads all 1e9 event rows into a Vec<EventVersionedRecord> and only then truncates to 10 — O(N) I/O and memory for a bounded query, despite an existing (be(sequence)-ordered) type index that could serve it in O(matches). `range_by_time(...)` on the same log allocates and sorts all 1e9 records per call.

**Suggested fix.** Serve get_by_type/get_by_type_at from the EventIndex via scan_prefix over encode_event_type_index_prefix(space,type) with the limit pushed down; add early-termination (stop after limit+1) to the sequence-window scan; answer range_by_time by binary-searching the monotonic append-time -> sequence relationship instead of full-scan+sort, or delete the unused index if these paths will not use it.

### 5. 🟠 HIGH · `graph` · conformance

**Cross-branch relationship bindings are accepted instead of rejected**

- **Location:** `crates/engine-next/src/data/graph/service.rs:275`
- **Governing spec:** entity-ref-and-relationship-layer-contract.md — Branch Scope rule 4 / Binding Decision 6 / conformance test 9; CLAUDE.md Hard Rule 18

**Issue.** `upsert_node` (and the `UpsertNode` arm of `batch_write`) stores `binding.clone()` and its binding-index row verbatim with no check on `binding.target().branch()`. `GraphBindingTarget::new` (types.rs:233) accepts an arbitrary `Option<BranchName>` with no validation. Nothing in the graph service, the type constructor, the record codec, or the key codec constrains the binding branch to the graph node's own branch. The contract is explicit: 'Graph relationship bindings reject cross-branch targets for V1' (Branch Scope rule 4) and 'V1 APIs reject cross-branch relationship bindings with a structured unsupported or failed-precondition status' (Decision 6). CLAUDE.md Hard Rule 18 states 'Cross-branch references are rejected.' A grep for cross_branch/failed_precondition/unsupported in the graph module returns nothing.

**Evidence.** service.rs:275 `if let Some(binding) = new_record.data().binding() { ... encode_graph_binding_record(&binding_record) }` — no branch guard; types.rs:233 `pub fn new(primitive, branch: Option<BranchName>, space, key) -> EngineResult<Self> { ... Ok(Self { primitive, branch, space, key }) }` — branch stored unvalidated.

**Failure scenario.** Open a graph service on branch `default`, then call `upsert_node("deps", "n", GraphNodeData::new(props, Some(GraphEntityBinding::new(GraphBindingTarget::new(GraphBindingPrimitive::Kv, Some(BranchName::new("secret")), space, "k").unwrap()))))`. The call returns Ok and persists a node + binding-index row whose relationship target points into branch `secret`. Conformance test 9 requires this to fail; instead it silently succeeds, and any future resolution of that binding crosses branch isolation.

**Suggested fix.** In upsert_node and batch_write's UpsertNode, reject when `target.branch()` is Some and != self.branch (or forbid Some entirely for stored bindings) with a structured `failed_precondition`/`unsupported` code before mutating; mirror the check in the record decoder to surface legacy cross-branch rows as unsupported.

### 6. 🟠 HIGH · `graph` · completeness

**No binding policy and no dangling/deleted/missing target status on bindings or traversal**

- **Location:** `crates/engine-next/src/data/graph/outcome.rs:379`
- **Governing spec:** entity-ref-and-relationship-layer-contract.md — V1 Minimum item 6, Reverse Maps rule 3, Dangling policy matrix, delete-policy vocabulary; primitive-implementation-contract.md §11; m6 plan M6C ('delete policies')

**Issue.** The relationship layer's central V1 promise — explicit dangling/deleted/missing/history-trimmed target status and a binding policy (strict-live / allow-dangling / pinned-provenance) — is entirely absent. `GraphEntityBinding` (types.rs:300) carries only a target, with no policy field. `GraphBinding` (outcome.rs:379) and `GraphNeighbor` (outcome.rs:303) carry no target-resolution-status field, so traversal and reverse-map lookups cannot report whether the bound entity exists. Interactive creation never validates that the target exists (no strict-live-target default). A grep across engine-next for any resolution-status/Dangling consumer of graph bindings finds none, so this is not implemented at a higher layer either. The contract makes target status a MUST ('Dangling/deleted/history-trimmed target status is explicit'), and M6C explicitly lists 'delete policies' as in-scope for this slice.

**Evidence.** outcome.rs:379-434 `struct GraphBinding { graph, node_id, binding, version, timestamp }` — no target status; outcome.rs:303-336 `struct GraphNeighbor { node, edge, direction }` — no target status; types.rs:300-317 `GraphEntityBinding { target }` — no policy.

**Failure scenario.** A graph node binds to JSON document `orders/ord_1`. The JSON document is later deleted. `bindings_for_entity(target)` and `neighbors(...)` still return the node with no indication the target is Deleted/Missing/Dangling, and there was never a policy recorded to say the binding was strict-live. Downstream (RAG/search/CLI) cannot filter or flag broken bindings as the contract's policy matrix requires.

**Suggested fix.** Add a `BindingPolicy` enum (StrictLive/AllowDangling/PinnedProvenance) to GraphEntityBinding and a target-resolution-status slot to GraphBinding/GraphNeighbor; wire interactive creation to validate targets by default through the persistence/orchestration resolver (graph must not fetch siblings directly).

**U8. 🟡 MEDIUM · correctness — A UUID-form branch name can alias the v5-derived id of an ordinary branch name; nothing rejects the collision**  
`crates/engine-next/src/branch/catalog.rs:256` · CLAUDE.md Hard Rules 16 & 18 (generations monotonic scoped per branch name; cross-branch references rejected); branch contract Binding Decision 11 (same-name recreation must not inherit stale state)

`derive_branch_id_text` returns the literal parsed UUID for any name that parses as a UUID (catalog.rs:260-262), while ordinary names hash to a UUIDv5. `aliases_reserved_branch_identity` only guards the three RESERVED ids (default, default-storage, system) — it does NOT check collisions with the derived ids of other user branch names (catalog.rs:242-254). So two distinct, valid branch names can map to the SAME branch_id and therefore the SAME storage_branch_id. Example: `derive("main") == 1f64c067-acf2-5034-a5d0-92d5764138ec` (proven by the locked anchor test at catalog.rs:275-280), and `derive("1f64c067-acf2-5034-a5d0-92d5764138ec")` returns those same bytes. The user gets a permanent-looking failure creating a fresh branch name, with an error referencing storage state they never knowingly touched.

*Fix:* Either scope generation/lifecycle by storage_branch_id rather than name, or reject a branch name whose parsed-UUID id collides with the derivable id of any other reachable name (or drop the raw-UUID-name shortcut for user-created branches). At minimum, detect storage_branch_id collisions at create time and return a structured `already_exists.engine.branch`-class error naming the aliasing branch instead of a raw storage generation error.

**U9. 🟡 MEDIUM · conformance — Historical fork falls back to copying LATEST vector manifests when the fork frontier has none — current derived state used for a historical point**  
`crates/engine-next/src/branch/service.rs:408` · temporal-context-and-timeline-resolver-contract.md — Binding Decision 10 ("Current derived state must never be used for historical correctness unless classified exact or source-filtered"); branch contract Binding Decision 10 (derived state explicit)

`materialize_vector_index_manifests_for_fork` first scans source vector-index manifests at the fork frontier (AtVersion(fork_version) or AtTimestamp). If that scan returns no rows, it retries the scan at `ReadSelector::Latest` (service.rs:408-415) and materializes the child's manifests from the source's CURRENT state. *Failure scenario:* Source branch has vectors; the vector index manifest for a collection is (re)written at commit V+5, and more vectors are added through commit V+20. *Fix:* Remove the Latest fallback for historical forks; if no manifest exists at the fork frontier, leave the child manifest absent (to be rebuilt) or mark derived state stale/rebuild-required per the derived-state contract, rather than importing current-frontier manifests.

### `control-plane`

**U12. 🟡 MEDIUM · correctness — Fork clears the pending marker after the storage branch is already durably forked, orphaning the branch and permanently poisoning the name**  
`crates/engine-next/src/branch/service.rs:191` · control-plane-layout-contract.md — Bootstrap/pending-marker fail-closed protocol; Branch Behavior > Create/Fork

The control-plane pending-marker protocol (control/bootstrap.rs begin_branch_operation / clear_pending_branch_operation / persist_branch_record) exists so an interrupted branch op fails closed on reopen. In fork_current (service.rs:186-193) and fork_with (service.rs:339-346) the storage branch is ALREADY durably forked (fork_branch_current returned Ok and describe_branch succeeded) before materialize_vector_index_manifests_for_fork runs. The name 'child' can never be created again (permanent denial) and X leaks storage.

*Fix:* On any failure that occurs AFTER the storage branch is durably created/forked, fail closed (leave the pending marker, mint terminal_error) instead of clearing the marker, or roll back by deleting the just-created storage branch before clearing. - **R1. `event` — Temporal reads (get_at/len_at/list_at/range_by_time/get_by_type_at) filter by engine-fabricated append timestamps over ReadSelector::Latest instead of the storage commit timeline**  
  _Why rejected:_ The finding's mechanical description is accurate — event temporal reads (get_at service.rs:168-170, len_at:190, get_by_type_at:219, list_types_at:323, list_page as_of:360, range_by_time:295) all use ReadSelector::Latest + a filter on event.timestamp(), which is the engine-fabricated wall-clock append timestamp (outcome.rs:124/435; normalized_event_timestamp service.rs:705-712 = observed.max(last+1) from SystemTime::now()), and the event code never uses AtTimestamp/AtVersion while KV/JSON do (kv/service.rs:119). It rests on the premise that the 5 events 'commit at storage-commit-time T' (a wall-clock value) and that a KV row read via get_at(key, T) with that same T is meaningfully visible — i.e., that event append time and the storage commit timeline share a domain.
